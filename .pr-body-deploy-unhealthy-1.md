# DEPLOY-UNHEALTHY-1: a deploy over an observed-unhealthy service plans the replacement

Climbs `gunbc.recurring_failure_mode a_deploy_that_observes_its_own_service_cannot_repair_it` to its
stated NEXT TRIGGER and adds the **third occurrence** to the row.

The next trigger, in the row's words: *"show a plan derive a replace-release step from an
unhealthy-but-observed service process."* Before this change, that plan could not be derived at all.

## The occurrence this closes

> On 2026-10-15 at 22:4xZ the operator-approved main-tip prod apply at 87cf694fb90 refused at plan
> with no mutation: "live_deploy: the deployment plan could not be derived from the host:
> service-process: refused -- could not observe the host: the process is active but /healthz refused:
> http client GET failed within the 240 s probe deadline derived from the serve wall limit; tailnet
> door cutover refused with no route effect: the cutover journal could not be read, so an interrupted
> cutover cannot be ruled out: read refused: reply undecodable: HTTP 502".
> Prod had been crash-looping since 2026-10-14 21:00Z (a half-applied deploy: new binary over the old
> tree). So the only modeled route to repair prod required prod to be healthy. Recovery is going out
> of band again (the operator decided to run tree-sync's own ExecStart by hand).

Prod was `ActiveState=active` — a unit in a restart flurry is active — while `/healthz` refused. The
observation folded that pair into **the same arm as "the host cannot be reached"**, so the deploy
that carried the repair refused to derive it, and recovery left the model for the third time.

## What changed

**Facet (a) — the service process now distinguishes an ANSWER from an ABSENCE, at every grain.**

- `extdeps.http.client`: new operation `GetWithinWithStatus` (+ `http_client_get_with_status_argv`).
  One curl invocation, **without** `--fail`, appending `-w "\n%{http_code}"`. curl's exit still
  separates the two cases, and it is the only thing that does: exit 0 means a response arrived (even
  a 503 — that is the whole point of no `-f`), nonzero means nothing answered. The body/status split
  is done by `extdeps.tools.curl`'s **existing** `classify_curl_http_code_after_newline` /
  `curl_body_before_http_code` — one authority for reading curl's write-out, not a second one.
- `gunbc.roadmap.roadmap_site_surface_types`: `HealthzEffectiveRead` gains
  `HealthzAnsweredUnhealthy { status, detail }`.
- `gunbc.live_deploy.readiness`: ONE status-aware fold (`healthz_effective_read_from_status_get`)
  routes the local, ssh and fleet probe legs. The routing is: a body that identifies a release is
  that release **whatever its status** (the identity authority `observe_running_release_identity`
  owns that verdict, not a status code); otherwise a server-error class answer (via
  `extdeps.ietf.http_semantics.http_status_class_of`) is `HealthzAnsweredUnhealthy`; anything else
  keeps the body's verdict; a curl failure is `HealthzProbeRefused`. `ServiceReadinessPending` gains
  `ServiceObservedUnhealthy { status, detail }`, which is Pending and **never Ready**.
- `gunbc.live_deploy.member_observe`: the `Active` leg yields
  `MemberObserved { ProcessAt { ProcessObservedUnhealthy } }` — an observation, not
  `MemberUnobservable`.
- `gunbc.live_deploy.member_identity`: `decide_member` takes the host's installed position
  (`InstalledReleasePosition`, read from the Tree member's **own** observation by
  `installed_release_position`, so the process arm and the tree arm cannot tell two stories about one
  host) and, over `ProcessObservedUnhealthy` on an Active unit: **Replace** when the installed
  revision differs from the candidate; `UnhealthyAtInstalledRelease` when it is the same (restarting
  would re-run the release that just refused); `UnhealthyReleasePositionUnobserved` when the position
  is unreadable. The decision lives in the domain assessment (D14), not in a generic Boolean, and the
  observer upstream only ever says what it measured.

Guards the row demanded, kept and claimed: an arbitrary 403 keeps its body verdict (never absent,
never a replacement trigger); a reply that identifies a release is read as that release; a transport
failure still refuses; an unreadable installed revision refuses rather than guessing a difference.

**Facet (b) — the door-cutover journal: nothing weakened.**

The journal read went through fabric storage, the very service this deploy repairs, answering 502.
Refusing because an interrupted cutover cannot be ruled out is sound safety and is **unchanged**:
`CutoverJournalNotReadable` and its refusal text are byte-identical, with zero route effects.

The cyclic precondition was a **starvation, not an ordering bug**. `live_deploy_tailnet_door_cutover_gate`
already runs *downstream* of the plan fold, and the admitted mutate steps restart the fabric-storage
unit unconditionally (`fabric_storage_admitted_mutate_steps`). The 2026-10-15 journal sentence appeared
because `apply.dag` *appends* the cutover reason to the plan's refusal — and the plan refused because
of facet (a). Once the plan derives, the store is repaired before its journal is read. So neither
candidate from the brief needed building: no member reordering, no deferred cutover. **The "proceed
with the door route unverified" fork was considered and declined** — a deploy may not repoint the
public door route with an interrupted cutover unruled out.

## Rung, honestly

CEILING 3 is reached **for the service-process facet** — that is what the row's ceiling stated, so the
row's own ceiling is met, not exceeded. The facet is not "closed" in a wider sense: a service unhealthy
for a reason a replacement cannot fix now refuses **loudly** (`UnhealthyAtInstalledRelease` /
`UnhealthyReleasePositionUnobserved`, naming the installed revision and what would change the answer)
instead of deadlocking, and that is a different subject than this row's. **The door-cutover facet is
climbed not at all** — its refusal is reproduced unchanged as a CONTROL, and the cycle was broken by
the ordering that already existed. Recorded in the row's `receipts`.
