# CI DAG Rendering: Multi-Provider Step Visibility

**Status**: Completed
**Date**: 2026-01-30

## Problem Statement

Currently, the entire CI DAG executes within a single workflow step:

```yaml
# Current: Single step, no visibility
- name: Run CI
  run: cargo run -p gunbc-ci -- run
```

GitHub Actions and GitLab CI both support step/stage visualization that we are not leveraging. The DAG structure naturally maps to these constructs - we should generate native CI YAML that gives good progress visibility.

## Key Insight: Fractal Generation

**The step subcommand comes for free!**

The `gunbc-ci` binary is already generated by `cli_gen.rs` from the `ToolDef` registry. The code generator:

1. Knows the graph builder function (`build_ci_graph`)
2. Can introspect the DAG at codegen time to discover all nodes
3. Can generate a `step` subcommand that executes individual nodes
4. Can generate help text listing all available steps

This means **no manual code** is needed for step execution - it's part of the existing code generation pipeline.

## DAG Structure

The CI DAG already encodes the dependency structure:

```
SetupDeps (gen 0) -> Prep (gen 1) -> Build (gen 2) -> Test (gen 2)  -> Report (gen 3)
                                                  \-> Lint (gen 2) -/
```

This structure can map to:

- **GitHub Actions**: Steps within a job (sequential) or multiple jobs (parallel)
- **GitLab CI**: Jobs within stages (parallel per stage)

## Design: DAG-to-CI Mapping

### Strategy 1: Steps per Node (GitHub Actions)

Map each DAG node to a workflow step with outputs:

```yaml
jobs:
  ci:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
      
      - name: Setup Deps
        id: setup_deps
        run: cargo run -p gunbc-ci -- step setup_deps
        
      - name: Prep (Codegen)
        id: prep
        run: cargo run -p gunbc-ci -- step prep
        
      - name: Build
        id: build
        run: cargo run -p gunbc-ci -- step build
        
      - name: Test
        id: test
        run: cargo run -p gunbc-ci -- step test
        
      - name: Lint
        id: lint
        run: cargo run -p gunbc-ci -- step lint
        
      - name: Report
        run: cargo run -p gunbc-ci -- step report
```

### Strategy 2: Jobs per Generation (GitHub Actions)

Map DAG generations to jobs (parallel nodes become parallel jobs):

```yaml
jobs:
  setup:
    runs-on: ubuntu-latest
    outputs:
      deps_checked: ${{ steps.run.outputs.deps_checked }}
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
      - id: run
        run: cargo run -p gunbc-ci -- step setup_deps prep

  build:
    needs: setup
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
      - run: cargo run -p gunbc-ci -- step build

  test:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable  
      - run: cargo run -p gunbc-ci -- step test

  lint:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
      - run: cargo run -p gunbc-ci -- step lint

  report:
    needs: [test, lint]
    if: always()
    runs-on: ubuntu-latest
    steps:
      - run: echo "Test=${{ needs.test.result }} Lint=${{ needs.lint.result }}"
```

### Strategy 3: Stages (GitLab CI)

Map DAG generations to GitLab stages:

```yaml
stages:
  - setup
  - build
  - verify  # test + lint parallel
  - report

setup_deps:
  stage: setup
  script:
    - cargo run -p gunbc-ci -- step setup_deps

prep:
  stage: setup
  script:
    - cargo run -p gunbc-ci -- step prep
  needs: [setup_deps]

build:
  stage: build
  script:
    - cargo run -p gunbc-ci -- step build
  needs: [prep]

test:
  stage: verify
  script:
    - cargo run -p gunbc-ci -- step test
  needs: [build]

lint:
  stage: verify  
  script:
    - cargo run -p gunbc-ci -- step lint
  needs: [build]

report:
  stage: report
  script:
    - cargo run -p gunbc-ci -- step report
  needs: [test, lint]
  when: always
```

## Step Input/Output Protocol

Define how steps communicate:

```rust
/// How step outputs are passed between steps
pub enum OutputProtocol {
    /// GitHub Actions: GITHUB_OUTPUT file
    GitHubOutput,
    /// GitLab CI: artifacts + dotenv
    GitLabArtifacts,
    /// Environment variables
    EnvVars,
}

/// Load inputs from the CI environment
fn load_step_inputs_from_env(node: &Node<CIOp>) -> HashMap<String, Value> {
    let mut inputs = HashMap::new();
    for port in &node.inputs {
        // Try STEP_{PREV_NODE}_{PORT} pattern
        if let Ok(val) = std::env::var(format!("STEP_{}_{}", 
            port.source_node.to_uppercase(), port.name.to_uppercase())) {
            inputs.insert(port.name.clone(), Value::from_env_string(&val));
        }
    }
    inputs
}
```

## Trade-offs

| Approach              | Pros                                 | Cons                             |
| --------------------- | ------------------------------------ | -------------------------------- |
| Single Step (current) | Simple, fast, all logic in Rust      | No step visibility in UI         |
| Steps per Node        | Good visibility, sequential          | Checkout/setup per step overhead |
| Jobs per Generation   | Parallel execution, great visibility | Checkout per job, complex YAML   |
| Hybrid                | Balance of visibility and speed      | More complex rendering logic     |

## Recommendation

**Start with Strategy 1 (Steps per Node)** for GitHub Actions:

- Good visibility with minimal complexity
- Single job means single checkout
- Steps show progress in GitHub UI
- Easy to implement (just add `-- step` subcommand)

**Later add Strategy 3 (Stages)** for GitLab CI:

- Natural mapping to GitLab's model
- Can leverage `needs:` for DAG execution
- Parallel test/lint in same stage

## Open Questions

3. **Fallback**: Should `gunbc-ci run` still work as single-step mode for local dev?

## Architecture Decisions

- Each CI provider (GitHub Actions, GitLab CI) owns its DAG-to-CI mapping
- Shared nodes (`SharedStep`) allow maximum code reuse
- Step mode is opt-in via `ToolMeta.enable_step_mode`
- YAML templates generated at codegen time, runtime DAG introspection for step mode
- `gunbc-ci` uses the **Bootstrap Pattern** - handwritten main.rs with upsert for codegen
