# DAG-Native CLI Contracts

**Status**: Draft
**Date**: 2026-02-06

## Problem Statement

CLI contract testing is currently the largest remaining block of codegen glue code.
The pipeline is:

```
registry.rs (hand-maintained ToolDef list)
  → cli_contract.rs generates Rust integration tests
    → test spawns binary as subprocess with --dry-run
      → binary parses args, prints key: value header
    → test parses stdout with string matching
    → test asserts header values match expected inputs
```

Issues:
1. **Subprocess overhead** — spawns a whole binary just to check arg parsing
2. **String-based validation** — fragile header parsing, no structured data
3. **Manual sample values** — `sample_string_value()` heuristics guess test inputs
4. **Duplicated source of truth** — `ToolDef` in registry.rs, `#[tool_target]` in lib.rs, `CliEntrypoint` schema, and the actual graph builder all describe the same tool differently
5. **Not on the DAG** — unlike testgen (boundary/chain/flow tests), contract tests aren't derived from DAG structure
6. **Cyclic dep barrier** — clippy can't use `#[testgen_target]` because `gunbc-clippy → gunbc-testgen-registry → gunbc-codegen → gunbc-clippy`

## Current State

### What codegen generates today

| Artifact | Source | Generator |
|----------|--------|-----------|
| `target/codegen/bin/*/main.rs` | `ToolDef` + `CliEntrypoint` | `cli_gen.rs` |
| `tests/generated_tests_cli_contract.rs` | `ToolDef` + `CliEntrypoint` | `cli_contract.rs` |
| `src/generated_tests.rs` (per crate) | `#[testgen_target]` + `MockSpec` | `testgen/codegen.rs` |
| Makefile targets | `ToolDef.invocation` + makegen registry | `makegen/` |

### What's already on the DAG

- **testgen** — generates boundary, chain, flow tests from `MockSpec` + DAG structure
- **content upsert** — `add_content_upsert_chain()` pattern for pragma, bootstrap, makegen, testgen
- **all 7 binaries** — bootstrap, makegen, ci, build, pragma, testgen, codegen

### The gap

CLI contract tests are the only test category still generated by the old codegen
path rather than derived from DAG structure. The generated `main.rs` files are
also codegen (arg parsing, mode selection, display), but they're harder to
eliminate since they're the entry point that bootstraps DAG execution.

## Design

### Key Insight

The CLI contract test checks exactly one thing: **did the CLI correctly parse
arguments into DAG entrypoint values?** This is a pure function:

```
parse_args(argv: &[String], schema: &[CliEntrypoint]) -> HashMap<String, Value>
```

Today this function is inlined in every generated `main.rs`. It should be a
library function that can be unit-tested directly — no subprocess, no stdout
parsing.

### Phase 1: Extract CLI Parser Library

Move the arg-parsing logic from `cli_gen.rs` code generation into a reusable
runtime library.

```
core/cli/src/lib.rs
  pub fn parse_cli_args(argv: &[String], schema: &[CliEntrypoint]) -> ParseResult
  pub struct ParseResult { args: HashMap<String, Value>, mode: ExecMode, ... }
```

The generated `main.rs` would call this library instead of inline parsing:

```rust
// Before (generated inline while-loop):
let mut repo_path = String::from(".");
while let Some(arg) = args.next() { match arg.as_str() { "--repo-path" | "-r" => ... } }

// After (library call):
let result = gunbc_cli::parse_cli_args(&args, &ENTRYPOINT_SCHEMA);
```

**Benefits:**
- CLI parsing becomes unit-testable without spawning binaries
- Contract tests become: `parse_cli_args(sample_argv, schema)` + assert on `ParseResult`
- Generated `main.rs` gets simpler (just call the library)
- Schema can be `const` in each crate (derived from `CliEntrypoint` definitions)

**Tasks:**
- [ ] Create `core/cli` crate with `parse_cli_args()`
- [ ] Define `CliSchema` as a static/const-friendly version of `Vec<CliEntrypoint>`
- [ ] Unit tests for parsing: scalars, repeatables, bools, defaults, missing required
- [ ] Update `cli_gen.rs` to emit `parse_cli_args()` call instead of inline loop
- [ ] Rewrite `cli_contract.rs` to emit in-process tests (no subprocess)
- [ ] Verify all 6 generated CLIs work with the new parser

### Phase 2: Declarative Entrypoint Schema

Today, entrypoints are defined in two places:
- `registry.rs` `all_tools()` — `CliEntrypoint` objects with flags, defaults, help
- `#[tool_target]` — crate_name, builder, mock_spec (but no entrypoints)

Merge these into the `#[tool_target]` annotation so the schema lives next to the
graph builder:

```rust
#[tool_target(
    name = "gist",
    builder = "build_gist_graph",
    entrypoints = [
        { port = "repo_path", type = "String", short = "r", default = ".", help = "Repository path" },
        { port = "extensions", type = "String", cardinality = "0..*", short = "e", help = "Extensions" },
        { port = "public", type = "Bool", short = "p", help = "Make gist public" },
    ]
)]
```

This eliminates the `all_tools()` registry entirely — `inventory` auto-discovery
provides everything.

**Tasks:**
- [ ] Extend `#[tool_target]` macro to accept `entrypoints` list
- [ ] Add entrypoint fields to `ToolTarget` struct in `core/tool-registry`
- [ ] Migrate each tool's entrypoints from `registry.rs` to `#[tool_target]`
- [ ] Delete `registry.rs` `all_tools()` (replaced by `iter_tool_targets()`)
- [ ] Update `cli_gen.rs` to read from `iter_tool_targets()` instead of `all_tools()`
- [ ] Update `cli_contract.rs` to read from `iter_tool_targets()`

### Phase 3: DAG-Derived Contract Tests

With Phase 1 (parser library) and Phase 2 (declarative schema), contract tests
become fully derivable from the tool registration:

```rust
// For each #[tool_target] with entrypoints:
//   1. Generate sample argv from the entrypoint schema
//   2. Call parse_cli_args(argv, schema)
//   3. Assert all entrypoints parsed correctly
//   4. Assert missing-required errors when expected
//   5. Assert type coercion works (string → int, etc.)
```

This can be folded into testgen — a new obligation bucket ("CLI contract") that
generates automatically when a `#[tool_target]` has entrypoints.

**Tasks:**
- [ ] Add `CliContractObligation` to testgen obligation model
- [ ] Generate contract tests from `#[tool_target]` entrypoints
- [ ] Generate negative tests (missing required, wrong type)
- [ ] Delete `cli_contract.rs` entirely
- [ ] Delete `generated_tests_cli_contract.rs` files

## Dependency Considerations

### The Cyclic Dep Problem

```
gunbc-clippy → gunbc-testgen-registry → gunbc-codegen → gunbc-clippy
```

Phase 2 helps here: if `all_tools()` is eliminated and replaced by
`iter_tool_targets()`, the `gunbc-codegen → gunbc-clippy` edge might be
removable (codegen wouldn't need to import clippy's types — it would discover
them via inventory at runtime). This would break the cycle and let clippy use
full `#[testgen_target]` annotations.

### What Stays as Codegen

The generated `main.rs` files are the bootstrap boundary — they must exist as
Rust source so cargo can compile them as binary targets. But with Phase 1, they
shrink to ~20 lines:

```rust
fn main() {
    let schema = &MY_TOOL_SCHEMA;
    let result = gunbc_cli::parse_cli_args(&std::env::args().collect::<Vec<_>>(), schema);
    let dag = build_my_graph(&result.args)?;
    gunbc_cli::execute_and_display(dag, result.mode, &result.mocks);
}
```

This is thin enough that it's more template than codegen.

## Migration Path

```
Phase 1 (parser library)          → contract tests become in-process
Phase 2 (declarative entrypoints) → all_tools() eliminated, cyclic dep breakable
Phase 3 (DAG-derived contracts)   → cli_contract.rs eliminated entirely
```

Each phase is independently shippable. Phase 1 alone eliminates the subprocess
testing pattern that caused the `CARGO_BIN_EXE` hyphen/underscore bug.
