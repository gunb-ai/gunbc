CLOCK_HANDLING, because the first pass of this probe got it wrong and the mistake was found in
review. Two clocks are in play and they are NOT interchangeable:
  * the OBSERVER clock -- this container's UTC clock, the only one used as the time of the
    observation, stamped per request into surface-ladder.txt (observer_utc column) and reported as
    observer_started_utc / observer_finished_utc above;
  * the BMC's OWN clock -- the Date header the controller stamps on its responses.
In this pass the two agree to about 3 seconds (first request: observer 04:00:12Z, BMC Date
"Tue, 27 Oct 2026 04:00:09 GMT"), so the BMC clock is currently close to correct and there is no
disagreement to adjudicate. That is a MEASUREMENT, not an assumption: the earlier pass
(...T005424Z) carried a service-root Date header reading 26 Oct 10:45:43 GMT against an observer
window of 00:54Z, a ~14h gap, which is why the two clocks are now recorded side by side instead of
one being trusted implicitly. A BMC clock that is wrong is normal (a reflash resets it; see
gunbc.recurring_failure_mode.firmware_reflash_resets_the_bmc_credential_it_needs) and is a reason
never to date an observation by a response header or a file mtime. Neither is used here.

WHAT THE LADDER ESTABLISHES, AND THE ONE THING IT CHANGES ABOUT THE READING.
  * GET /redfish/v1/ -> 200 with Server "AMI MegaRAC Redfish Service". The controller DOES serve a
    Redfish service on 0.45. This is the finding that retires the 0.32-era "serves no Redfish"
    premise (gunbc.machine_intake.mtcollins1_access_observation, taken 2026-09-11 under 0.32, where
    every /redfish path 404'd).
  * Body verbatim: RedfishVersion "1.8.0", @odata.type "#ServiceRoot.v1_5_2.ServiceRoot" (that is
    the ServiceRoot SCHEMA version, 1.5.2 -- NOT the Redfish protocol version, which is the
    RedfishVersion field), Id "RootService", Name "Root Service", Vendor "AMI", Product "AMI Redfish
    Server", UUID "2254ee50-beb6-1000-01e6-4cd68a3cc128", and top-level service links AccountService,
    CertificateService, Chassis, CompositionService, EventService, JsonSchemas, Managers, Registries,
    SessionService, Systems, Tasks, TelemetryService, UpdateService, plus Links.Sessions and an
    Oem.Ami subtree (RtpVersion "13.02", configurations, InventoryDataStatus).
  * EVERY Redfish resource and collection below the root -> 401, offering Basic and X-Auth-Token
    (realm AMI_Redfish_Server). So TransferProtocolType, which lives in the VirtualMedia member
    bodies, is not readable anonymously.
  * TWO DIFFERENT SERVERS ANSWER THIS ONE ADDRESS, and the ladder shows it: the /redfish paths are
    served by "AMI MegaRAC Redfish Service" while /api/session, /api/settings/media/general and /

    attestations, not one service's behaviour -- relevant because the 0.32 reading saw 404 on the
    Redfish paths while the web root served 200, which is exactly what a lighttpd-only front looks
    like. Reading "the box has no Redfish" off a host that serves 200 at / and 404 under /redfish
    conflated the two servers; the Server header is what distinguishes them, and it is now captured.

IDENTITY (why this is a read of the UNIT and not merely of an address) -- stated at the strength the
capture actually supports.
  * The FRU Board Extra in the committed intake capture is "28C13C8AD64C" and the reserved endpoint
    MAC is 28:C1:3C:8A:D6:4C (artifacts/bmc/mtcollins1-intake-ipmi.json, endpoint_mac and
    ipmi_fru_print_0).
  * Reversing that MAC's byte order gives 4cd68a3cc128.
  * The service root served in THIS pass carries UUID 2254ee50-beb6-1000-01e6-4cd68a3cc128, whose
    final 12 hex digits are exactly 4cd68a3cc128.
  * The host's own SMBIOS UUID, read from the machine in artifacts/bmc/mtcollins1-host-capture.txt,
    is d5b80e46-903a-1000-01e6-4cd68a3cc128 -- which shares that same final-12-digits MAC encoding.
  * WHAT THAT DOES AND DOES NOT PROVE. It does NOT show the BMC UUID and the SMBIOS UUID are equal;
    they are NOT equal (they differ above the MAC field). What they share is the MAC encoding, and
    the MAC is corroborated independently by the FRU Board Extra. So the claim the capture supports
    is: the controller answering on 192.168.1.228 reports a UUID encoding the unit's own burned-in
    BMC MAC, and the host on that board reports a UUID encoding the same MAC. The address, the
    served Redfish service and the unit are the same box. No claim of UUID equality is made, because
    the evidence does not carry one.
