## Three distinct families, not one root

The `the trait bound X is not satisfied` pattern covers 547 of 603 tree-wide occurrences (per-module: 06_translate 70, 04_infer 69, 05_eval 74, 05_emit 70, emit_host 115, emit_module 70, materialization_carriers 79 — see the TSV; verified by direct `awk` summation, not estimated). The remaining 56 are a residual present in **every** module (see the Residual section below, corrected from an earlier draft that only examined `materialization_carriers`). 547 + 56 = 603 exactly. The matched portion decomposes cleanly into three families that do **not** share a fix:

1. **Generic-type-parameter `Clone` (the dominant family, ~26-30 occurrences/module, present in every module).** `T: Clone`, `U: Clone`, `A: Clone`, `B: Clone` — bare, unbounded generic type parameters used at emit sites that require `Clone` but carry no `where T: Clone` bound in the emitted Rust signature. **Confirmed by reading the raw diagnostic context (not just the first-line grep) for every T/U/A/B:Clone occurrence in `06_translate`: every site is a struct-declaration derive** — e.g. `pub struct FreeMonoidUniqueState<T> { pub seen: Rc<Vec<T>>, ... }` deriving `Clone`/`Debug`/`serde::Serialize`/`serde::Deserialize`, where the struct's own generic param list carries no `T: Clone` bound even though its field (`Rc<Vec<T>>`/`im::Vector<T>`) requires one. A smaller subset (e.g. `freemonoid_empty<T>() -> Rc<Vec<T>>`) is a plain fn signature. **This rules out the existing `v1_generic_params_needing_clone_bound`/`v1_emit_type_params_with_clone_bounds` mechanism (`src/v1/trait_derive_emit.dag:157,177`) as already covering this family**: that mechanism is wired only into `emit_fn_def` (`src/v1/05_emit_rust.dag:5172`, function-signature emission) and is never called from `emit_type_def_from_connective` (`src/v1/05_emit_rust.dag:4609-4615`, struct/enum-declaration emission, which renders generic params via the plain `emit_type_params` with no Clone-bound logic at all). Since every observed failure site here is a struct declaration, the existing mechanism structurally cannot reach it — it is real, correctly implemented for its own narrow scope (return-type-is-the-generic or generic-used-as-a-collection-element in a *function* signature), but is not the fix for this family.
   - **This is very likely the E0599 root, viewed from a different call shape.** The E0599 partial census (handed off to swift-bee-52) found the dominant pattern there was `no method named \`clone\` found for type parameter \`T\`/\`R\`/\`A\`` — same type-parameter letters (T/U/A/B/R), same missing-Clone defect. E0599 fires when the generic is used as a bare receiver (`x.clone()` with no method resolution possible at all); E0277 fires when the call *does* resolve (often via an explicit `Clone::clone(&x)` or a trait-object/where-clause context) but the bound isn't declared. Same underlying gap: **the emitter does not propagate a `Clone` bound onto generic type parameters that need it**, just observed through two different rustc diagnostic codes depending on how the generic is consumed at the use site.
   - This is the family to root-cause first before any fix slice — it's the shared root with E0599, and fixing it once should shrink both buckets simultaneously across all seven modules.

2. **`Node`/`EnvironmentBindingKey` missing `Hash`/`Eq` (5-6 occurrences/module, present in every module).** `Node: std::hash::Hash`, `Node: Eq`, `EnvironmentBindingKey: std::hash::Hash` — these carriers are used as map/set keys (`HashMap<Node, _>` or similar) in emitted code without the emitter having verified or derived `Hash`/`Eq` on the source type. Distinct from family 1 — no correlation with E0599's clone/is_empty/iter pattern. Likely a missing-derive gap at the struct/enum declaration → emit boundary for these two specific carrier types.

3. **`serde::Serialize`/`Deserialize` missing on interpreter/carrier structs (present in every module at a fixed ~3:1 Deserialize:Serialize ratio; `emit_host` and `materialization_carriers` additionally carry a large `CommutativeSemiring<Magnitude>` sub-family).** `ValueInterpreter`, `TransformInterpreter`, `MatchInterpreter`, `LoopInterpreter`, `BranchInterpreter`, `BindInterpreter`, `EffectIoEvalBundle` (05_eval/emit_host only) each miss `serde::Deserialize<'de>` (3x) and `serde::Serialize` (1x) — the 3:1 ratio suggests three call sites deserialize a value of that type per one that serializes it (not obviously a bug in itself, just the call-shape ratio at those particular carriers). `CommutativeSemiring<Magnitude>` is the single largest contributor tree-wide: 30 (Deserialize) + 6 (Serialize) in `emit_host`, 45 (Deserialize) + 9 (Serialize) in `materialization_carriers` — **this alone explains most of emit_host's and materialization_carriers' outlier totals** (129 vs the 76 baseline, and 90 respectively). Distinct root from families 1 and 2: a missing `#[derive(Serialize, Deserialize)]` on `CommutativeSemiring<Magnitude>` and the six/seven `*Interpreter`/`EffectIoEvalBundle` structs.

Emitter site located: `emit_type_def_from_connective` (`src/v1/05_emit_rust.dag:4609`) renders struct/enum generic params via the plain `emit_type_params` (`src/v1/05_emit_rust.dag:4565`) with no Clone-bound logic. **Correction (review 43338):** the fix is NOT "add `T: Clone` to the struct's own declared generics." Checked against the vendored `im` crate source (`im-15.1.0/src/vector/mod.rs:145`, `src/ser.rs:235,244`): `pub struct Vector<A>` itself carries **no** bound, and `impl<A: Clone> Clone for Vector<A>` needs only `Clone`, but `impl<A: Clone + Debug> Debug for Vector<A>` and the `Serialize`/`Deserialize` impls each need `Clone` **in addition to** their own trait. Rust's naive `#[derive(Debug)]`/serde-derive only add the trait's own per-param bound (`T: Debug`/`T: Serialize`/`T: Deserialize`), never the extra `Clone` some fields' own conditional impls also require — that's the actual gap, and it is scoped to *specific derived impls*, not the type itself. Putting `T: Clone` on the struct's own generic list would over-constrain every use of the type (construction, field access, anything not needing Debug/Serialize/Clone) — a fabricated, broader-than-justified constraint, not a derived one. The correct fix is per-derive-target: `#[serde(bound(serialize = "T: Clone + Serialize", deserialize = "T: Clone + Deserialize<'de>"))]` overrides for serde, and a hand-written `Debug` impl (or equivalent per-impl bound emission) in place of `#[derive(Debug)]` — never a blanket struct-level bound. The existing fn-only mechanism (`v1_generic_params_needing_clone_bound`/`v1_emit_type_params_with_clone_bounds`, `src/v1/trait_derive_emit.dag:157,177`) still doesn't reach this path and isn't the right model to extend here regardless — that predicate targets the type itself, not a specific trait impl's bound list.
