## The mechanism, established by execution rather than by reading

Every one of the 31 sites carries rustc's `note: match arms with guards don't count towards
exhaustivity`. That note is the whole story, and it points at the emitter.

gunbc#8570 (`52e1c4dc6c`) stopped the emitter from silently swallowing sibling arms when a
nested constructor pattern sits under an `Rc`-bound field: the nested pattern became a plain
`ref` binding plus a `matches!` **guard** plus a `let … else { unreachable!() }` prelude. Rust
ignores guarded arms when it checks exhaustiveness, so any outer variant covered *only* by such
arms is reported uncovered. The census receipt recorded the same conversion independently on
`emit_module`: `unreachable_pattern 37 → 0` while `E0004 1 → 28`
(`docs/probes/v2_compiler_emission_census_2026-08-19.md`).

The emitted arm, read from a single-module emit of `v2.std.refinement_widening_predicate` at
this ref rather than inferred from the emitter source:

```rust
Outcome::Accepted { value: source_value_set, ref diagnostics, .. }
    if matches!(diagnostics.as_ref(), None) =>
    { let None = diagnostics.as_ref() else { unreachable!() }; … }
Outcome::Rejected { diagnostics: _, .. } => false,
```

`Diagnostics` is a non-unit-only coproduct, so it is in `shared_types` and its `None`
sub-pattern is Rc-ref-bound — which is why a field that looks like a plain `Option` match is
guarded at all.

## Why "guarded" is not by itself the diagnosis

A guard explains the *message*; it does not establish that the source was exhaustive. Those are
different claims and the population splits on exactly that distinction. Discriminating control,
run against rustc directly rather than reasoned about:

```rust
match o {
    Outcome::Accepted { value: _, diagnostics: None } => true,
    Outcome::Rejected { diagnostics: _ } => false,
}
```
→ `error[E0004]: non-exhaustive patterns: 'Outcome::Accepted { diagnostics: Some(_), .. }' not
covered`, **with no guards note**.

So an unguarded `diagnostics: None` narrowing is *already* non-exhaustive, and reports the
precise missing case. Our sites report the **bare** `Outcome::Accepted { .. }` instead. The
guard is therefore doing two things at once: it loses exhaustivity, and it **replaces a precise
missing-case message with an imprecise one**. Removing the guard reveals which sites had a real
source gap underneath and which did not — and that is the partition below.

## The partition

Three roots, distinguished by whether the `.dag` source is exhaustive once the guard is removed.

| **D — source pins `diagnostics: None`, never handles an `Accepted` carrying diagnostics** | v2 `.dag` sources | see below |
| **V — source covers only some inner value cases** | v2 `.dag` sources | see below |

Worked instances of each, cited by symbol:

- **G.** `v2.compiler.infer` matches on `dag_canonical_literal_from_node` (5 sites) cover

  `discovered_source_refs_digest_eq` is the same shape one level in:
  `DiscoveredSourceRefsDigestUnavailableCause` has a single variant, so
  `Unavailable { cause: NoRefList { … } }` covers its whole variant.
- **D.** `v2.std.refinement_widening_predicate` `refinement_widening_value_sets_hold` and its
  siblings, `v2.std.integer_value_set`, `v2.std.integer`, `v2.std.host_run`, `v2.compiler.eval`
  — each writes `Accepted { value: …, diagnostics: None }` beside a `Rejected` arm and nothing
  else, so an `Accepted` carrying advisories has no arm. The control above proves this is a real
  gap independent of the guard.
- **V.** `v2.std.compilers.target_model` (an inner `value: false` and two
  `TargetTypeExprArrowWireShape` variants uncovered) and `v2.std.grammar`
  `rebuild_production_match_fold`, which covers `Holds { value: RebuildEmittedOk { … } }` but not
  `RebuildEmittedFail` — a declared second variant of `RebuildEmittedResult`.

**Why the exact per-root counts are deliberately not tabulated here from static reading.** A
site's root is decided by whether the inner match is exhaustive once the guard is gone, and the
authority for that is rustc on the re-emitted tree, not a human reading arms. The counts land in
the re-measurement section as an observed conversion — which class became which — rather than as
a net, per this document's sibling census and DESIGN §4b's rung-honesty rule.

## What v1 does and does not check

`v1.compiler.patterns` `check_match_exhaustiveness` is real and runs
(`v1.compiler.infer` calls it), but it decides coverage at **variant grain**: a match naming
`Accepted` and `Rejected` is exhaustive to it. A refinement *inside* an arm — `diagnostics: None`,
`value: RebuildEmittedOk { … }` — narrows the covered set without removing a variant name, and
nothing in v1 sees that narrowing. Roots D and V are therefore invisible to the `.dag` frontend
and are caught only by rustc after emission, i.e. by a downstream realization rather than by the
compiler that accepted the program. That is a floor gap in DESIGN §4b's sense — closed variants
are supposed to eliminate exhaustively — and it is named here rather than left to be rediscovered.
It is not repaired by this probe: sub-pattern-grain exhaustiveness is its own lane, and it would
refuse a live source population that has to be repaired in the same motion.

## The defect this measurement caught in the fix itself

The first version of the grouping keyed on the emitted outer pattern **string**. It measured
**E0004 31 → 32 with a new `unreachable_pattern: 6`** — errors, not lints, since the emitted crate
carries `#![deny(unreachable_patterns)]`. Two arms of one outer variant can emit different outer
patterns:

```
NodeKind::TypeNode { ref connective, .. }   -- discriminates the field
NodeKind::TypeNode { connective: _, .. }    -- does not
```

String keying made those two groups, the first lost its guard, and rustc then reported it as
*"matches all the relevant values"* with the second arm *"no value can reach this"*. That is the
silent-wrong-answer class #8570 exists to prevent, reintroduced at six sites
(`v2.compiler.normalize`, `.resolve`, `.eval`, `.translate`,
`v2.std.compilers.target_model`, `v2.extdeps.languages.dag`).

The key is therefore the outer **variant**, and a variant is grouped only when every arm carrying
it is groupable and agrees on both the emitted pattern and the discriminated field. That is
strictly narrower — it is why the residue above is 6 rather than 0 — and the narrowing is the
point: a guarded arm is a visible E0004, a shadowed arm compiles clean and changes behaviour.

Recorded because the count alone would have hidden it. `31 → 32` reads as a rounding error; the
six dead arms underneath it did not.

## Reconciling the `diagnostics: None` population — the predicate, not the number

An earlier revision of this receipt reported "71 `diagnostics: None` occurrences in `src/v2`"
with no predicate beside it. `zesty-carp-454`, working the same state from the B4 door, reported
349 from a same-looking grep. Both numbers are real and they answer different questions, which is
exactly why a count published without its predicate is not a measurement. Each figure below names
the command that produces it.

| predicate | command | count |
|---|---|---|
| any `diagnostics: None` text | `grep -rn "diagnostics: None" src/v2` | 561 |
| …construction sites (no `=>` on the line) | same, `grep -v "=>"` | 436 |
| **match arms pinning `diagnostics: None`** | `grep -rnE "^\s*Accepted \{[^}]*diagnostics: None \}\s*=>" src/v2` | **71**, in 26 files |
| match arms pinning `diagnostics: Some` | `grep -rnE "^\s*Accepted \{[^}]*diagnostics: Some" src/v2` | **4** |
| match arms binding `diagnostics` to a name or `_` | `grep -rncE "^\s*Accepted \{[^}]*diagnostics: (_\|[a-z][a-z_]*) \}\s*=>" src/v2` | **2286** |

Multi-line arms are not a hidden tail: zero occurrences put `diagnostics: None }` at end of line
with the `=>` on the next, so the 71 is the whole single-line arm population, not a lower bound.

**The 71 is a population, not a defect count.** An arm pinning `None` is only a gap where no
sibling covers `Accepted`-with-`Some`, and deciding that needs the match, not a line. The
executed, decided subset is the **15** root-D sites in this closure, which rustc adjudicated.

**The last row is the most interesting one and it was not visible from the E0004 board at all.**
The corpus binds `diagnostics` totally — to a name or `_` — **2286** times, against **71**
narrowing arms and only **4** arms anywhere that pin `Some`. So the repository already answers
"is an `Accepted` carrying diagnostics still accepted?" in the affirmative, by construction,
thirty-two times for every time it narrows. The 71 are the deviant minority, and the near-absence
of `Some` arms is why almost none of them has a sibling.

That is evidence about the modelling question rather than about this PR: it argues against adding
a third `Outcome` variant, since a third state would have to be threaded through 2286 sites that
are already total and correct under the two-variant reading. It is recorded here because the
number that matters to the modelling lane is 2286, and it is invisible to anything counting errors.
