## Root 1 is not a missing derive. It is an impossible one.

Every carrier in root 1 holds a **function-valued field**, directly or transitively:

| carrier | function-valued field | via |
|---|---|---|
| `ValueInterpreter` | `allocate_literal: fn(..)` | direct |
| `TransformInterpreter` | `call_primitive: fn(..)` | direct |
| `MatchInterpreter` | `choose_arm: fn(..)` | direct |
| `LoopInterpreter` | `step_loop: fn(..)` | direct |
| `BranchInterpreter` | `choose_branch: fn(..)` | direct |
| `BindInterpreter` | `bind_value: fn(..)` | direct |
| `PartialFunction<K,V>` | `lookup`/`get`/`insert`/`merge: fn(..)` | direct (`std.algebra`) |
| `CompiledLexRule` | `thunk` | → `LexMatchThunk.apply: fn(String) -> LexMatchResult` |
| `EffectIoEvalBundle` | `handlers` | → `EffectHandlerBinding.read_resource` → `EffectHandler.handle: fn(..)` |
| `dyn Fn(..) -> ..` | — | is itself a function value |

The requiring site is always an **outer** struct that derives serde and holds one of these:

```
error[E0277]: the trait bound `CompiledLexRule: serde::Deserialize<'de>` is not satisfied
 499 |     pub rules: Rc<Vec<Rc<CompiledLexRule>>>,
help: the trait `Deserialize<'_>` is not implemented for `CompiledLexRule`
     = note: for local types consider adding `#[derive(serde::Deserialize)]` to your type
```

**rustc's own suggested fix is wrong here, and it is the fix a fresh lane ships first.** Adding `#[derive(serde::Deserialize)]` to `CompiledLexRule` cannot succeed — a `fn(..)` field implements neither `Deserialize` nor `Serialize` nor `Debug`. The derive would fail *at the carrier instead of at its consumer*: the error moves, the count may even fall, and nothing is fixed.

This is the same shape as review 43338's correction to `e0277_trait_bound_census_2026-07-26.md`, where a blanket struct-level `T: Clone` type-checks, reduces the count, and is wrong.

**The decidable question is upstream of the derive:** the emitter derives `Serialize`/`Deserialize`/`Debug` on v2 carriers, and a type transitively containing a function-valued field can never satisfy those. Whether a type reaches a `fn` field is a structural property of the declaration — decidable, so it is a construction wall rather than a validation (DESIGN.md §5). The repair lands in the derive decision (`trait_derive_emit.dag` / `05_emit_rust.dag`), which is why this packet was routed to this session.

## Answering the Rc question directly

Asked: does a large slice dissolve under the Rc-wrap root another lane is already fixing?

- **Root 4 (9)** — `expected a Fn(_) closure, found Rc<dyn Fn(_) -> Rc<Outcome<_>>>`. Plausibly yes; this is a function value wrapped where the callee wanted the bare closure. **Do not repair these here.**
- **Root 1 (60)** — **no.** Unwrapping `Rc` does not help: `fn(..)` itself implements none of these traits, so the bound fails identically on the unwrapped form. This slice is independent of the Rc work.

So **at most 9 of 100 dissolve**, not a large slice. The 60 needs its own repair and the two lanes do not collide.
