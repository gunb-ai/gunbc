gunbc runner host serial capture -- Mt. Collins, host attempt runner-canary-6-83b96b35, 2026-09-07

THIS CAPTURE WAS FIRST COMMITTED UNDER THE WRONG IDENTITY, AND THE CORRECTION IS THE POINT.
It was published as the host evidence for actions run 34090864879 -- a job that SUCCEEDED. This
boot did not run that job. It fetched no credential, refused to start a runner, and panicked:

    jitconfig-bytes=0
    RUNNER REFUSED: /dev/vdb carried no JIT configuration

The join was made on the shared string "runner-canary-6", which is a BUILD label reused across every
power cycle of that image. The concrete host attempt is runner-canary-6-83b96b35. One-shot JIT
delivery means only ONE boot of that build could ever have run the job, so a build label can never
identify which one did.

WHAT ACTUALLY HAPPENED, and it is worse than a mislabelled file. The harness power-cycled the host
up to four times looking for a boot it could observe. An earlier cycle ended with

    SOL session closed by BMC

which the harness scored as "did not reach our loader" -- but a dropped CONSOLE is not a failed BOOT.
That boot continued, fetched the one-shot credential, registered, and ran the job to success at
06:37:54. The harness, seeing nothing, POWER-CYCLED A MACHINE THAT WAS RUNNING A LIVE CI JOB, and
this capture is the credential-less boot that followed.

SO THE HOST EVIDENCE FOR THE SUCCESSFUL RUN DOES NOT EXIST. It was never captured, and no digest or
extract can conjure it. That is stated rather than papered over, and gunbc.runner.runner_qualification_receipt
now says so.

THIS CAPTURE IS KEPT BECAUSE IT IS THE MORE VALUABLE ARTIFACT. It records a fail-open the intended
receipt would never have shown: with a ZERO-BYTE credential the host went on to create the JIT
drive, create the workspace, and LAUNCH FIRECRACKER anyway. The refusal happened inside the guest,
after a VM had already been started. It also shows Firecracker exiting with status 0 after that
guest panicked -- so a clean VMM exit is not evidence that any work ran.
