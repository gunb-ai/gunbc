## §1. What L1.5 delivers

Four independent deliverables, all shippable in parallel:

1. **Pipeline composition declaration** — the compiler's own
   pipeline as a typed `.dag` composition
2. **Per-stage fixed-point** — regen verifies each stage
   produces identical output across passes
3. **Test authority types** — `std/verification.dag` with
   structural types for generated tests
4. **Ownership Phase 1** — fan-out counting + basic clone
   elision (fully designed in
   `docs/ownership-rendering-design.md`)

## §2. Pipeline composition declaration

### §2.1 v3's stage list

v2 has 9 stages. v3 currently has 4 in code:

```
parse → lower → infer → emit
```

With ownership as a pipeline-computed fact (not a lens), v3's
pipeline is:

```
parse → lower → infer → ownership → emit
```

Lenses (complexity, effects, trace, etc.) are orthogonal to
stages. They read the Dag but don't transform it. The compiler
composes on top of lenses — it may consult a lens to make a
decision (e.g., emit reads ownership facts to choose
move/clone), but the lens itself is not a pipeline stage.

**Default lenses.** Some lenses should run on every program by
default (complexity, ownership). These are opt-out, not opt-in.
The pipeline declaration specifies which lenses are default:

```dag
fn compile(source: String, file: String, spec: LanguageSpec) -> CompileResult {
  let parsed     = parse(source, file)
  let lowered    = lower(parsed)
  let inferred   = infer(lowered)
  let ownership  = compute_ownership(inferred)
  let complexity = lens_complexity(inferred)  // default lens
  emit(inferred, ownership, complexity, spec)
}
```

Lenses that are NOT default (e.g., a user-defined analysis lens)
can be composed in by the caller without changing the pipeline.

### §2.2 Intermediate types

Each stage produces and consumes typed values. The question is:
does every stage traffic in `Dag`, or do we need distinct types?

**Answer: `Dag` is the universal intermediate, but stages
declare what they ADD to it.**

v3's `Dag` is a mutable accumulator — `parse` populates
surface items, `lower` populates declarations and behaviors,
`infer` populates port types. Each stage's "output type" is
the same `Dag` but with more facts filled in. The typed
contract is not "this stage returns `InferredDag`" — it's
"after this stage, all ports have `Resolved` state" (a
lens-checked property per SELF_HOSTING.md §2.1).

For the pipeline declaration, stages are `fn(Dag) -> Dag`
with documented postconditions:

```dag
// Stage postconditions (lens-checked, not type-level):
// parse:     SurfaceModule populated, tokens consumed
// lower:     Declarations + Behaviors populated, surface items consumed
// infer:     All ports have PortState::Resolved or diagnostic
// ownership: OwnershipFact computed for every port
// emit:      Target source text produced
```

**Parse is the exception** — it takes `(String, String)` and
produces the initial `Dag`. All subsequent stages take `Dag`
and return `Dag`.

### §2.3 Where the pipeline declaration lives

The compiler owns the pipeline. It lives in
`src/v3/compiler/pipeline.dag` (new file, sibling to the
existing `.rs` compiler sources).

The pipeline draws from `std/` for types (ValueSemantics,
SharingModel, TestClaim) but the pipeline composition itself
is compiler infrastructure, not user-facing std/ modeling.

During L1.5, the pipeline declaration is just the typed
signatures with `ExternalRealization` bodies — the Rust code
IS the implementation. The `.dag` bodies come at L3.

### §2.4 Error gating between stages

Each stage may produce diagnostics. The pipeline's error
handling follows two rules:

1. **Fail-closed at each stage boundary.** If a stage produces
   diagnostics, subsequent stages still run but operate on the
   Dag-with-diagnostics. No silent skipping. Every stage
   handles the possibility of upstream diagnostics gracefully
   (a port with `PortState::Unresolved` is already handled by
   fail-closed patterns throughout infer/emit).

2. **No information loss.** Diagnostics from stage N are
   preserved through stages N+1, N+2, ... to the final output.
   The pipeline never drops a diagnostic. The `DiagnosticTable`
   is append-only across stages.

v2's explicit gates ("if resolve produced errors, do not
proceed") exist because v2's IR can't represent partial
failure. v3's `PortState::Unresolved` + fail-closed accessors
already handle partial failure structurally — a downstream
stage sees the Unresolved port and emits its own diagnostic
rather than crashing. The pipeline doesn't need explicit gates
because the substrate already prevents the crash case.

**The compile-to-dag boundary.** `compile_to_dag` returns
`Result<Dag, CompileError>`. The `Semantic(Dag)` variant
carries the Dag-with-diagnostics. The caller decides whether
to proceed (e.g., emit anyway for debugging) or stop. This
boundary stays as-is.

## §3. Per-stage fixed-point

### §3.1 What fixed-point means

The regen loop compiles the compiler's own `.dag` source twice:
pass1 (using the existing compiled pipeline) and pass2 (using
pass1's output as the compiler). If the pipeline is correct,
pass1 and pass2 produce identical output.

v2 checks this at the file level — "did the output files
change?" v3 checks at each stage boundary — "did stage N's
output change between pass1 and pass2?"

### §3.2 Stage snapshot format

Each stage produces a `Dag`. The snapshot is a **serialized
Dag** — a deterministic representation of the Dag's
declarations, behaviors, ports, and diagnostics.

The serialization must be:
- **Deterministic.** Same Dag → same bytes. No HashMap ordering
  nondeterminism.
- **Structural.** Compares declarations, connectives, behaviors,
  port states — not memory addresses or allocation order.
- **Diffable.** When pass1 != pass2, the diff names the first
  divergent declaration/behavior/port.

**Implementation shape.** A function
`fn serialize_dag(dag: &Dag) -> Vec<u8>` that walks
declarations in ID order, behaviors in ID order, ports in ID
order. Each element serialized deterministically. Comparison is
byte equality. Diff is first-divergent-byte with structural
attribution.

This is a new function in the compiler crate. It does not need
to be a `.dag` lens yet — it's Rust infrastructure for the
regen loop. At L3, it migrates to `.dag` alongside the rest of
the pipeline.

### §3.3 Regen flow

v3 needs a regen equivalent. The pipeline declaration (§2)
makes this structural:

```bash
# regen.sh (or equivalent)
#
# 1. Compile the .dag pipeline source using the current binary
# 2. Capture per-stage Dag snapshots at each boundary
# 3. Compile the same source using the pass1 output
# 4. Capture per-stage Dag snapshots again
# 5. Compare snapshots at each boundary
# 6. Report first divergent stage, if any
```

The regen flow is specified AS PART of the pipeline — it's not
a separate meta-pipeline. The pipeline declaration already
names the stages and their boundaries. Regen reads the same
declaration and snapshots at the same boundaries.

**Acceptance criteria (from SELF_HOSTING.md §11):**

- [ ] `regen.sh` captures per-stage Dag snapshots during
      pass1 and pass2
- [ ] Fixed-point check compares snapshots at each boundary
- [ ] Divergence reports the first divergent stage and the
      structural delta
- [ ] Tested against a synthetic divergence (intentionally
      break one stage, verify the error names it)

## §4. Test authority types

### §4.1 What goes in `std/verification.dag`

Three structural types that define what a test IS:

```dag
module std.verification

type DiagnosticKind
  = TokenizerError
  | ParseError
  | TypeMismatch
  | ArityMismatch
  | ResolveError

type DiagnosticExpectation
  = KindIs(DiagnosticKind)
  | ResolveNameContains(String)

type TestPredicate
  = Compiles                          // program compiles with zero diagnostics
  | FailsWithDiagnostic(DiagnosticExpectation)
  | OutputEquals { expected: String }     // emitted code matches expected string
  | PortResolved { bind_name: String }    // named bind's output port is Resolved
  | PortUnresolved { bind_name: String }  // named bind's output port is Unresolved
  | CostBelow { bound: Int }              // structural cost is at or below bound
  | CostAbove { floor: Int }              // structural cost is above floor

type TestClaim {
  name: String
  source: String              // the .dag program text
  file_name: String           // the file name for diagnostics
  predicate: TestPredicate
}

type TestSuite {
  name: String
  claims: List<TestClaim>
}
```

**Bootstrap staging note.** During L1.5 this file lives in
`src/v3/std/verification.dag`, not `dsl/std/verification.dag`,
because the v2 recursive `dsl/` CI pipeline still cannot ingest
the current v3 grammar. The older `dsl/std/verification.dag`
remains the v2-era behavioral-assertion model; it is not
silently superseded. Convergence trigger: when v2 retires and the
shared std tree can host the v3 verification surface directly,
dissolve the duplicate definitions back to one
`std.verification`.

`TestPredicate` is a Disj of verifiable properties. Each
variant is structurally checkable by the compiler — no
external oracle needed. The predicate set grows as the
compiler's verification surface grows (e.g., `CostIsProven`
when the complexity lens lands).

**Coproduct status.** `TestPredicate` is a **🟡 scaffold** at
L1.5. The richer source facts already exist in the compiler
substrate (`Diagnostic`, `PortState`, structural cost ordering),
but L1.5 does not yet surface them as reusable std/ carriers the
verification layer can point at directly. Dissolution trigger:
once those authorities are available as first-class std values,
split the remaining compressed port-state and cost variants into
those axes before more runtime consumers attach. The diagnostic
branch is already decompressed one step into
`DiagnosticExpectation`, so generated claims do not overload one
raw string with multiple meanings.

### §4.2 First consumer: structural testgen

The first consumer of `TestClaim` is structural test
generation from types declared in `std/`:

For every `type T { ... }` in `std/`:
- Generate a `Compiles` claim: a program that constructs a
  valid `T` value
- Generate a `FailsWithDiagnostic` claim: a program that
  constructs an INVALID `T` value (wrong field type, missing
  field, extra field)

For every `type T = A | B | C` in `std/`:
- Generate a `Compiles` claim per variant
- Generate a `FailsWithDiagnostic` claim for non-exhaustive
  match

This is a lens that reads the type declarations and emits
`TestClaim` substrate values directly. Rust-side tests consume
those values by inspecting their lowered structural form; the
host language does not mirror the `std.verification` schema.
The test runner compiles each claim and checks its predicate. No
hand-written test programs.

### §4.3 Rendering to target test frameworks

Each target language has a test framework:
- Rust: `#[test]` + `assert!`
- Go: `func Test...` + `t.Fatal`
- Python: `def test_...` + `assert`

The emitter reads `TestClaim` values and renders them to the
target's test framework using the same `RealizationIndex`
pattern as type/operator emission. `TestClaim` is a type in
`std/`; its rendering is a realization in `rust.dag`.

This is L2.6 work (behavioral testgen). L1.5 declares the
types; L2.6 builds the generation lens and the rendering.

All four deliverables are independent. Parallel work is safe.

| 1 | Pipeline declaration | `src/v3/compiler/pipeline.dag` (new), `src/v3/compiler/src/bootstrap.rs` (loads it) | ~30 lines .dag, ~20 lines bootstrap | None |

**Sequencing recommendation:**
- Start 1 + 3 + 4 in parallel (three independent worktrees)
- Start 2 after 1 lands (needs the stage boundaries)
- 4 has the most immediate impact (every generated artifact
  benefits from clone elision)
- 1 has the most architectural impact (sets the shape for
  everything that follows)

## §7. What this unblocks

Once L1.5 ships, four parallel tracks open:

- **L2** — lens migrations (complexity, effects, trace). The
  pipeline composition gives lenses a structural home. The
  clone-elision from ownership Phase 1 means migrated lens
  code doesn't carry 90+ unnecessary clones.
- **L2.5** — per-stage domain modeling. The pipeline declaration
  names the stages; L2.5 models each stage's domain types in
  `std/` and `extdeps/`.
- **L2.6** — testgen + dry-run. The test authority types from
  deliverable 3 are the structural foundation.
- **L2.7** — ownership Phases 2-3. Phase 1's consumer-count
  index and SharingModel are the foundation for escape analysis
  and full ownership proof.
