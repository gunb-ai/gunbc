# Handoff — v2 native parse-population: rebuild SpanIndex from the committed tree

Session: keen-stag-70 · node adhoc-99a9c3c9-d02 · revision measured: `708057ca` (session/keen-stag-70 @ origin/main)
Manager: quiet-raven-506. Decision (msg_987cd07e / msg_58cd9647): **re-target** — do NOT build the emitter projection-move rule; hand off this spec. No PR from this session.

## 0. One-paragraph diagnosis

`v2-native-cli ... parse-population` costs ~90–130 ms/file, superlinear. ~60–66% of native parse wall-time is materializing the per-node `SpanIndex` (a persistent `im::HashMap`) that the parse **verdict never reads**. It is threaded as an accumulator through a **backtracking** parser, so every `span_index_record` insert is a HAMT copy-on-write against a live prior snapshot (the pre-choice `prov` held open across the alternatives loop). This is the persistent structure correctly preserving pre-choice state — NOT a lowering defect — so the fix is not in the emitter but in the parser's **design**: the index should not be threaded through tentative parses at all; it should be built once from the committed tree where a consumer demands it.

## 1. Measurements (all native `--release`, serial, on the emitted parse-compiler closure; rev `708057ca`)

Ladder = synthetic governed-tree samples of N single-`decl` statements (~12 tokens/decl). Baseline wall (best of 2–3):

| sample | baseline | span-index elided (diagnostic) |
|---|---|---|
| ladder2000  | 3.18 s  | 1.60 s |
| ladder8000  | 12.78 s | 4.30 s |
| ladder16000 | 30.92 s | 8.19 s |

Superlinearity lives entirely in the index: baseline 8000→16000 (2× size) = **2.42×** (superlinear); span-index elided = **1.90×** (linear, per-decl flat ~0.5 ms). Eliding the index builders on ladder8000 = 12.78→4.30 s (**2.8×**).

Self-time profiler, ladder8000, ~12.8 s wall, self ns/call×count: `span_index_record` 2.61 s (608,013 × 4.30 µs), `stamp_conj` ~1.9 s, `repeat` ~1.7 s, `nonterminal` ~0.9 s, grammar eval (dispatch/sequence/terminal/choice_plan/optional/expr_with_first/furthest) ~1.8 s total, `rt_lookup` ~0.2 s. Tokenize+read+sha256 < ~2% (tokenizer ~0.5–0.6 ms/KB; the manager's own 14–16 s / ~10,100-file read+hash point agrees).

**M1 — insert scope.** RAII backtrack-depth guard incremented on entry to the 5 clearest speculative combinators (`parse_choice_ordered_backtrack`, `parse_choice_plan`, `parse_expr_repeat_step`, `parse_expr_expect`, `parse_expr_not_predicate_attempt`); depth>0 = tentative. On ladder8000, of **608,013** `span_index_record` inserts: **608,004 tentative (99.9985%), 9 committed (0.0015%)**. 9 is an UPPER bound on truly-committed inserts (only 5 frames wrapped; any unwrapped frame can only move more to tentative). Mechanism (confirmed in emitted `parse_choice_ordered_backtrack`): the loop holds `prov` across the whole alternatives loop and passes `prov.clone()` per attempt, so even the WINNING alternative runs with `prov` shared → its inserts are copy-on-write too.

**M2 — Option A (emitter move) upper bound.** A uniquely-owned in-place insert needs ZERO open backtrack frames → ≤ 9 inserts qualify. Empirically: applying the move transform by hand to `span_index_record` (`Rc::try_unwrap` base + `rc_map_insert(base.entries, …)`) + the 5 callee sites (unwrap `prov`, move `provv.index`) + 2 hot dead-after caller moves gave `IDX_UNIQUE = 0`, ladder unchanged. So A cannot pay off for the parser; A's ceiling ≈ 0.0015%.

**Microbench** (im 15.1, same map/same insert): aliased `im::HashMap` insert **1.7–3.7 µs** (grows with map size) vs uniquely-owned/consuming **0.38–0.52 µs** (~6–8×); `std::collections::HashMap` insert 0.10 µs. `im::HashMap::clone()` itself is O(1) (23 ns) — the cost is im copy-on-writing the refcount-shared HAMT root→leaf path, not the clone.

**Fail-closed proofs** (Option A was fail-closed, real rustc-checked moves, no `mem::take`/`replace`): moving `b.f` out of an Rc'd `b` (e.g. `result.prov`) → rustc **E0507** "cannot move out of an Rc"; `prov` moved into a call then a later `prov.alloc` use → rustc **E0382** use-of-moved-value. A wrong liveness call is a compile error, never a silent empty map.

### Why threading is the defect
`span_index_record(index: prov.index, ...)` runs per node; the record-update (`entries: map_insert(index.entries, ...)`) is a persistent-map update, and because the parser holds the pre-`prov` snapshot alive across backtrack frames (M1), each `entries` update copy-on-writes the whole HAMT path — superlinear. The verdict path (`v2/cli/population_verbs.dag`, and the emitted population verb) reads only `tree`/`diagnostics`/furthest — **never** `artifact.span_index`. So parse-population pays the full index cost for a value it discards, and compile pays the superlinearity for a positional index derivable from the committed tree.

### Target shape (matches manager's decision)
1. **Keep the allocator threading EXACTLY as is** (byte-identical ids gate, below). `alloc_occurrence_id` call sites, count, and order must not change. Keep `ParseProvenanceState { alloc }`; the `alloc` half stays threaded through the same provisional/committed rollback (choice clones `prov`, keeps the accepted branch's `alloc`).
2. **Nodes carry the index's two facts** at mint/complete time, on the node (or its occurrence) rather than a global map:
   - terminal (`parse_mint_from_source`): the node already mints `OccurrenceMinted{id}` and an `origin_event_from_source(locus)`. Attach the `OriginEvent` (FromSource locus) and, since a terminal's extent IS its FromSource locus (provenance.dag L43), its `RecordedSourceExtent`.
   - composite (stamp_*): attach the `DerivedBy{producer, from}` event, and the composed extent — computed **from the children's own extents** (see 3), recording `SourceExtentKnown` or `SourceExtentUnrepresentable` on the node.
   - Suggested representation: add to `NodeOccurrenceIdentity::OccurrenceMinted` (and Projected) a `recorded: Optional<(OriginEvent, RecordedSourceExtent)>`, OR a parallel field on `Node` — the smallest carrier the compiler's structural equality/hash (Fnv1a64) tolerates. VERIFY the node structural-hash/digest used elsewhere is not perturbed by the new field (if it is, carry it out-of-band or gate it out of the digest).
3. **Answer the mid-parse extent read from the children, not the global map**: `parse_extent_span_step` (L954/961) currently reads `span_index_extent(index, child_id)`. Replace with reading each child node's OWN recorded extent (its attached `RecordedSourceExtent`, falling back to its FromSource locus). Preserve the three-valued fold exactly (Known / Unrepresentable absorbing / no-extent-is-empty) so a composite still publishes the SAME extent it does today. **DESIGN §6b caveat:** the parser must still *publish* the extent it held (the comment at provenance.dag L44–51: a future consumer, roadmap `parse-comment-gap-attachment`, reads `span_index_extent` for containment; "nobody reconstructs a range from descendants"). Publishing per-node at parse time (not reconstructing on read from grandchildren) satisfies this.
4. **Build `SpanIndex` once from the committed tree at the demand point.** `ParseArtifact.span_index` (L5058) becomes a build from `tree`: fold the committed tree, and for each node whose `occurrence_id` carries an id, insert `(id → OriginEvent)` into `entries` and `(id → RecordedSourceExtent)` into `extents`; set `scope: Absent` (parse seeds Absent today; ingest sets scope later via `span_index_in_scope`, unchanged). Do it **lazily where a consumer demands it**: `authored_regions`/`authored_region_walk` (compile) and any `artifact.span_index` reader. **parse-population must not build it** (it reads no reader) — so the population walk pays only the (linear) per-node attach, not the threaded COW.
5. `authored_region_walk` may read node extents directly (child's own recorded extent) instead of via the rebuilt index — same values, cheaper; if kept reading the rebuilt index, build-from-tree first.

## 3. integration_concern row — emitter projection-move gap (record now, do NOT build)

Suggested row `gunbc.integration_concern`, kind capability-gap:
> **Title:** v1 emitter never moves a uniquely-owned accumulator field into a persistent update (`rc_map_insert`/`rc_map_merge`/list-push/set-insert), so a linear accumulator copy-on-writes on every update.
> **Body:** The record-update lowering emits `rc_map_insert(record.field.clone(), k, v)`; the `.clone()` aliases the persistent `im::HashMap`, forcing `Rc::make_mut` to copy-on-write the HAMT path instead of the unique in-place path. Measured (im 15.1, native --release): aliased insert 1.7–3.7 µs (grows with map size) vs uniquely-owned/consuming 0.38–0.52 µs (~6–8×); `std::collections::HashMap` 0.10 µs; `im::HashMap::clone()` O(1) 23 ns (cost is im COW of shared nodes, not the clone). Root-generalizes to EVERY emitted v2 binary's map/list/set accumulation. The emitter already has the pieces (v1_compiler_ownership `build_movable_set`/`moved_at_its_only_argument` move whole dead bindings as args; `FoldAccUnwrapProof`/`fold_body_safe_field_moves` move `.fold` accumulator fields; `analyze_dying_base_sites` for TCO-only record reuse) but NONE covers a *projection* (`b.f`) of a threaded, non-`.fold` accumulator. **Narrow sound rule (fail-closed, verified):** move `b.f` into a persistent-update receiver when it is that binding's last use, the use is the receiver (first arg), it does not flow under a lambda / loop back-edge, and `b` is not used whole after except through disjoint fields; in the record-builder `Rc::try_unwrap(base).unwrap_or_else(|rc| (*rc).clone())` and move the field in (shared stays a correct clone). Wrong liveness = rustc **E0507** (move out of Rc) or **E0382** (use-after-move) — never `mem::take`/`replace`/placeholder. **Not built now** because the parse-population hot path's sharing is backtracking (legitimate persistent structure), so this rule cannot pay off there — see the parse re-target (this doc). Build it for non-backtracking accumulators (fold/ingest/state-thread) as its own change; per DESIGN §6b it should subsume `FoldAccUnwrapProof` + the TCO-only `dying_base_sites` as instances (fold in / delete leaves, or keep + justify).
