## Two-failure-carrier reminder (carriage discipline)

The acceptance table below distinguishes the **two structurally distinct failure carriers** in the lens stack, per `design-lens-framework.md` §2 + `design-lens-application-surface.md` §5 — these are **not** interchangeable; conflating them would push implementation toward the wrong carrier:

1. **Lens read-channel `Witness<C>::Violates { reason, at: Behavior }`** — `read(dag, behavior)` could not find a substrate fact for that `Behavior` (e.g. an op with no declared cost per `design-lens-framework.md` §"Three worked instances" Instance 1). This is a **per-Behavior missing-fact** signal; it is **never** the carrier for "computed value exceeded declared budget".
2. **Application-enforcement typed `Diagnostic`** — produced when `LensEnforcement.violates(output, budget)` returns `true` during the `EnforcedApplication` walk (per `design-lens-application-surface.md` §5 step 2 + §4.1 worked example). The fold-pass emits this `Diagnostic` directly and accumulates it into `DimensionFail.violations: List<Diagnostic>` (per `design-lens-framework.md` §2 `DimensionReport` shape). The fold may also surface it as a compile-time Diagnostic when `diagnostic_severity: Error`.

**AC-2-RED / AC-3-RED test the enforcement-Diagnostic carrier** (computed value exceeds declared budget); **`Witness::Violates`** is reserved for missing-read-fact rows. The two are reported together inside the same `DimensionReport` but originate from different code paths.
