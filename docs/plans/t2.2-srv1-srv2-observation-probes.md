## The questions, answered

### Q1 — which modeled observation yields a typed receipt for a host never observed before (srv2)

**`gunbc.fleet.fleet_converge_plan_cli` (host-grant observation, `gunbc.fleet.fleet_host_grant_coverage`)
is the model that yields a typed first-observe receipt without an apply.** Its shape
(`fleet_host_grant_coverage.dag:68-101`) admits the never-observed state as its own typed arm —
`HostGrantPrincipalUnobserved` (`data host_grant_observation_unobserved_no_transaction`, :103) — rather
than collapsing "absent" into "converged" (DESIGN §3d: unselected ≠ deferred ≠ refused ≠ converged;
§4d: "cannot rule out" ≠ "ruled out"). Reading it runs no actuation: the plan route never writes
runner state beyond its own receipt/artifact files.

**What is missing so it can be read for srv2 without an apply (three gaps, all verified at the call site):**

1. **Roster gap.** `fleet_converge_host_names()` (`fleet_converge_cli.dag:67-71`) lists
   `[operator_host_srv1, operator_host_srv3, operator_host_srv4]` — srv2 has no plan row, so the plan
   route can currently only emit "host not in roster" for srv2. The probe below tests this empirically.
2. **Transport gap.** The wet reader executes its sudo legs with `transport: LocalExec`
   (`fleet_converge_plan_cli.dag` `observe_host_grant_decision_wet` → `run_shell_command_capture(..., transport: LocalExec)`
   over `extdeps.sudo.nopasswd_decision.sudo_decision_command` = `sudo -n -ll`). It therefore reads the
   machine the process runs on — the self-hosted runner at srv1 — never srv2. The over-fleet-ssh variant
   exists only in the file route (`gunbc.runner.fleet_ssh_execution.typed_argv_exec_over_fleet_ssh`).
3. **Principal gap.** On srv2 (`runner_host_deploy.dag:128-134`) the ssh login is `briansrls@192.168.1.188`
   while the job user is `ghrunner` — and on srv1 they differ too (`admin` vs `ghrunner`). The file route's
   sudo reader probes the SUBJECT LOGIN's standing (`RunnerHostPrivilegeStanding`,
   `runner_host_file_converge.dag:1235`, leg `LegAdministratorPrivilegeProbe` = elevated `true` at :1162),
   while grant observations target the job user. A probe that conflates the two principals misreads.

The other two candidates, for completeness:
- `gunbc.runner.runner_host_file_converge` observe mode DOES yield a typed run receipt for a
  never-observed host over fleet-ssh (subject admission via `administrator_ssh_target`, legs = list-units,
  show-slot-properties, residue load-state, privilege probe), but what its sudo reader yields is the
  privilege STANDING, not the grant list.
- `extdeps.sudo` (the sudo reader: `nopasswd_decision.dag`, typed arms `SudoNoPasswd |
  SudoPasswordRequired | SudoNotPermitted | SudoCommandNotPermitted`) parses ANY `sudo -n -ll` output into
  a typed decision on a first-ever read — but it is transport-bound to the machine it runs on (LocalExec),
  so it cannot reach srv2 by itself.

### Q2 — srv1 cgroup readback against the slot shape (`gunbc.runner.runner_slot_desired`)

Desired shape, verified at the data: `runner_slot_desired.dag:173-174` — `memory_max:
byte_size(23622320128)` (= 22 GiB exactly) and `memory_swap_max: byte_size(0)`.

**The route that reads the live cgroup files exists — `gunbc.runner.runner_slot_cap_converge.read_slot_cap_live_over_fleet_ssh`
(`runner_slot_cap_converge.dag:~420`)**: it reads `systemctl show <unit> -p ControlGroup`
(`data slot_cap_show_properties: [MemoryMax, MemorySwapMax, MemoryHigh, TasksMax, ControlGroup]`, :28)
and then `cat /sys/fs/cgroup/<ControlGroup>/{memory.max,memory.swap.max}`
(`data slot_cap_cgroup_files`, :31), folding into the typed `SlotCapStanding`
(`HostCapAtDesired | HostCapOwed | HostCapUnreadable`, :54-57) with per-unit
`SlotCapUnitStanding = SlotCapAtDesired | SlotCapOwed | SlotCapDrifted | SlotCapUnreadable`
(:225-230 — `Drifted` = the dropin bytes are correct but the LIVE read differs; the daemon never
reloaded/restarted after an edit). It is a pure read: refusals resolve before stdout is looked at (:394-398),
so a grep that printed then failed can never read as a standing.

**The gap: no read-only entry point invokes it.**
- Its only wet path today is `run_runner_host_cap_phase` (`runner_host_file_converge.dag:2172-2180`),
  which returns `CapPhaseNotOwed` in `RunnerHostFilesObserveOnly` — the cgroup readback runs ONLY in the
  `RunnerHostFilesApply` arm.
- `gunbc.host.host_runner_memory_cap_verify` (`runner_memory_cap_verify_run`, :324) verifies unit-level
  MemoryMax/MemorySwapMax via `systemctl show` (the systemd EFFECTIVE view) but does not read the cgroup
  files, and has **no wet entry point at all** — its only caller is `converge_cli_verify_run`
  (`fleet_converge_cli.dag:557`), which no workflow dispatches.

So: the typed cgroup-vs-desired comparison exists and is discriminating; what is missing is a read-only
invocation. Cheapest honest probe today: `mode=runner_host_file_observe` on srv1, which reads
slot-properties + population + privilege (but NOT the cgroup files). Getting the cgroup files without an
apply needs either (a) a wet entry over `read_host_cap_standings_over` (a thin new entry, no apply path),
or (b) lifting the cap-phase READ legs (not the write legs) into observe mode — a model change, not mine
to make in this task.
