2382	// this note was written (review 68965). The receipt was written and nothing read it, while this
2383	// paragraph asserted the stage consumed it, so the only release evidence stage 2 actually had was
2384	// the revision the process reports on /livez: a launch argument this emitter writes into ExecStart,
2385	// echoed back whatever tree the unit loaded. The reader now exists
2386	// (gunbc.auth.approval_broker_cutover observe_broker_tree_receipt, consumed by
2387	// dark_install_release_discharged), which is what makes the sentence true rather than aspirational.
2388	//
2389	// WHAT IT ESTABLISHES, at its real strength: the copy for THIS candidate ran and recorded a digest,
2390	// which a stale tree from an earlier deploy fails. What it does NOT yet establish is that the
2391	// installed digest equals one computed independently over the deploying checkout -- that needs the
2392	// source-side digest at readback time and is named as the open half beside the reader. Without it the only evidence is the revision
2393	// the unit reports on /livez -- and that revision is a LAUNCH ARGUMENT this emitter wrote into
2394	// ExecStart, so the process echoes whatever it was told regardless of which bytes it loaded. A
2395	// control-plane fact standing in for the subject observation is the substitution
2396	// gunbc.recurring_failure_mode control_plane_acknowledgement_minted_as_effect exists to refuse; the
2397	// tree digest is the subject-side fact that closes it.
2398	//
2399	// ONLY THE INSTALLED DIGEST IS WRITTEN HERE, and that is a deliberate simplification over recording
2400	// both sides. The first cut of this command computed the SOURCE digest too, inside the emitted
2401	// shell, which meant a nested command substitution inside a printf inside an install -- four levels
2402	// of quoting hand-escaped in a string literal, unverifiable without rendering, and a malformed
2403	// quote fails the stage in a way that looks like a copy failure. The comparison does not need to
2404	// happen in shell: the readback runs IN the deploying checkout, so it computes the source digest
2405	// itself and compares against what it reads here. Shell reports one fact; the fold decides.
2406	// ONE ROOT IN, BOTH PATHS DERIVED. An earlier cut of this took the release directory AND the broker
2407	// root as separate parameters, which let a caller hand it a pair that did not correspond -- hash one
2408	// release and write the receipt into another -- and made the release directory a fact two folds knew
2409	// independently. The directory the digest covers and the directory the receipt lands in are the same
2410	// directory by construction now, which is a stronger statement than any check over two arguments.
2411	//
2412	// 🟡 dissolve-on: the step below assembles a `printf … | sudo install /dev/stdin` pipeline
2413	// as a string (medium-as-string, the same class approval_broker_tree_digest_expr marks); it
2414	// dissolves when v2.workflow.bash_emit can render a piped command from modeled parts.
2415	// THE RECEIPT IS WRITTEN BY THE PRINCIPAL THAT OWNS THE LOCUS: `install -m 0644 /dev/stdin`
2416	// into a root-owned directory needs root, and the digest pipeline feeding it is the same either way.

2418	  locus_tree_receipt_step_at(owner: owner, dir: approval_broker_release_dir(root: base_root, revision: revision), revision: revision)

2432	      join([dir, "/", release_locus_tree_receipt_name], "")]), " "),
