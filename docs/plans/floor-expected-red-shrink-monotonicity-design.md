# Design — monotone roster contract on `floor_expected_red`: undispositioned SHRINK refuses

**Status:** DRAFT, design-note-first (dashboard node `adhoc-48905ef9-c1d`, session stern-carp-58; scoping brief from sharp-raven-273, `msg_e9871ee7-6399-4d4c-b29e-2e7ce4ea5af0`). Not implemented; no code lands from this note yet.

## 1. The incident, and why growth was never the exposed direction here

`gunbc#8437` severed `floor_expected_red_chunks` — the aggregator returned `Empty {}` while the twenty chunk functions still held 464 identities and the header still read `POPULATION: 464`. The roster evaluated to zero on `main` for roughly an hour; every downstream check that reads it passed **vacuously** over the empty set. `#8446` closed that one shape: an empty roster now refuses (`ExpectedRedRosterEmpty`).

Zero is not the only silently-permitted state. The same incident window moved the roster three times — 469 → 464 → 358 — and nothing mechanical told those moves apart: one was an accident, one was deliberate, and the diff looked identical to every consumer. A finer read of the `#8437` rechunk shows the actual shape of the risk: it dropped 197 identities (661 → 464, zero added) while restructuring the chunks. Those 197 resolved, on manual review, into three disjoint buckets:

| bucket | count | what happened |
|---|---:|---|
| legitimately greened | 164 | the witness kept executing and started passing — a real repayment |
| genuinely stale | 28 | the witness itself is gone from the corpus — nothing to enroll |
| wrongly dropped | 5 | the witness still exists, still needed enrollment, and the row vanished under an in-flight session |

A roster can lose a hundred identities and still read as healthy, because `floor_expected_red`'s own self-emptying mechanism (an enrolled row that *executes and passes* reds the build until removed — see `expected_red_arm` / `stale_quarantine` in `required_floor`) only protects the rows that are **still enrolled and still discovered**. It says nothing about a row that disappears from the roster text itself. `floor_expected_red.dag`'s own 2026-08-18 rung-drop section states this gap in so many words: *"a roster that silently went 469 -> 361 is indistinguishable, to every mechanism in the tree, from [an undetected defect]... An empty roster now refuses; a shrinking one still does not."* This note is that sentence's fix.

## 2. What already exists, and is reused rather than re-derived

`gunbc.witness_deferral_freeze` is the same shape at the opposite polarity, and its host half — `collect_frozen_path_deferral_additions` / `collect_frozen_path_deferral_additions_for` / `collect_stale_frozen_path_deferrals` in `cli_run.rs` (~19260–19640) — already solved the two hard sub-problems this contract needs:

- **The baseline is not a literal.** `gunbc.diff_baseline` is the single authority for the comparison window; it crosses the seam as `FreezeBaselineComparison` (`Direct{base,head,kind}` | `MergeBase{base,head,kind}`), mirroring the typed carrier `FloorDiffComparisonReadout`. The gate's own history documents two forks already made and repaired here: hardcoding `origin/main` forked the *source*, and later imposing merge-base on every arm forked the *relation* (silently passing real growth on a rewritten push). Both are load-bearing scars, not stylistic choices — the new gate must consume `floor_diff_comparison_readout()` exactly as the freeze gate does, not re-derive a baseline.
- **Confirmed absence vs. failure to observe.** `read_frozen_roster_at_commit` distinguishes "the file is not in this tree" (`git ls-tree` succeeds, empty) from "I could not read it" (`git show` fails) — the same distinction this contract needs when the roster itself is younger than the compared baseline.
- **The workspace-is-at-the-resolved-head coherence check runs before any permitting arm.** This ordering was wrong when the freeze wall first landed (a confirmed-absence permit sat above it, and could answer about the wrong commit); the fix is now load-bearing history in the comment and must not be re-lost by a fresh implementation.
- **A count is not an oracle.** `frozen_path_deferral_count_is_a_receipt_note` states this explicitly for the freeze roster, and the same fact holds here with an even sharper edge: the roster is authored from the current tree, so comparing `len(roster)` before and after is a change detector, not a check — it would have missed `#8437`'s 464→464 rechunk-with-loss entirely had the rechunk been arithmetically balanced, and it says nothing about *which* identities moved. Every check below is at identity grain, never a count.

**Constraint carried forward from the brief, and binding on this note:** the freeze's realization is already ~505 production lines in `cli_run.rs`, registered as a `Scaffold` with its own ordered dissolution because it is the largest hand-maintained Rust wall in the program. This contract is **an instantiation of that machinery at inverted polarity, not a second authority** — landing a second several-hundred-line block beside it is exactly the §3 nicknaming violation the whole DESIGN document is organized to forbid. §4 below is deliberately a refactor-and-reuse plan, not a from-scratch implementation, and if the reuse does not hold cleanly the correct outcome is to say so and bring it back as a finding rather than pay the cost twice quietly.

## 3. The inverted polarity, and why it cannot be a pure diff-time check

|  | `witness_deferral_freeze` | `floor_expected_red` (this note) |
|---|---|---|
| roster meaning | legacy path-deferred witnesses tolerated but not required to execute | witnesses required to execute, currently known to fail |
| escape hatch | **adding** a row (re-opens a witness that runs nowhere) | **losing** a row (re-opens a witness that runs, still fails, and no longer reds) |
| refused direction | growth relative to baseline | shrink relative to baseline, *unless dispositioned* |
| oracle for the permitted direction | none needed — shrink is always safe here | a typed, per-removed-identity disposition |

The freeze gate is pure git plumbing: it never has to run anything, because "did this identity's roster row exist at the baseline" is answerable from two tree reads. This contract cannot be that cheap, for a reason visible directly in the incident: the danger case (a witness quietly stops being *discovered* — `#8437`'s severed aggregator, or a file moved outside `discovery_scan_dirs`) is invisible to git diff alone. A `git diff`-only version of this gate would see "row removed, nothing else to check" and permit exactly the incident it exists to prevent. So the gate has two layers, not one:

**Layer A — the git-diff layer (reused, inverted).** Generalize `collect_frozen_path_deferral_additions_for`'s pure fold `frozen_path_deferral_additions_in(current, base) -> Vec<String>` (currently `current \ base`) into a shared primitive that also returns `base \ current` — the removed set — under one shared baseline-resolution/coherence-check core. This is the concrete "generalize, don't duplicate" ask: one function computing `RosterDelta { added, removed }` against `FreezeBaselineComparison`, parameterized over which roster file and which line-parser to use, consumed by both gates (freeze reads `.added`, refuses on nonempty; this contract reads `.removed`, and does not refuse on it directly — it hands it to Layer B).

**Layer B — the disposition layer (new, and this is the actual design content).** For every identity in `removed`, classify it against the **current run's own evidence**, not against git history, because "does this witness still exist and pass" is a fact about the corpus and the floor's execution, not about the diff:

1. **Retired** — the identity's underlying test decl is no longer resolvable in the corpus at all. Verified by the same decl-scan join `collect_stale_frozen_path_deferrals` already performs (`scan_test_decl_lines` over the entry file; absent file or absent decl name both qualify). This is the mechanical, no-new-ledger disposition, and it is the one that covers the "28 genuinely stale" bucket automatically — a witness that is gone cannot be silently un-reded, because there is nothing left for it to un-red.
2. **Repaid** — the identity's decl still resolves, is still discovered by this run, and its outcome is `ClaimOutcome::Pass`. This is the one disposition that cannot be decided from git history at all: it requires correlating the removed-set against the *current run's* per-claim outcomes, which only exist after (or during) `run_required_floor` executes. This is the structural reason Layer B cannot live purely in the pre-flight diff step the freeze gate uses — it is necessarily a post-execution correlation inside (or immediately after) the required-floor fold, joined identity-grain against the git-diff `removed` set from Layer A. Anything discovered-but-not-passing, or simply **not discovered this run**, fails this test — which is precisely the fail-closed behavior that would have caught `#8437`: an identity dropped from the roster whose witness is *not discovered* this run is neither Retired (its decl still exists) nor Repaid (it never ran), so it falls through to refusal.
3. **Superseded** — an operator-approved relocation, e.g. today's `long/`-home rung-drops. This is a policy fact, not an observable one, and per DESIGN §5 ("a dissolution condition describes how admitted debt ends, it does not authorize creating the debt... approval is external to the diff") it must not be self-declared by the PR that performs the removal. This is the one bucket with no existing mechanical precedent to reuse cleanly and is the open question in §5 below.

Tested against the 197-identity split named in the brief: 164 land in Repaid, 28 in Retired, and the 5 wrongly-dropped identities land in **none of the three** — which is the correct outcome, since they should have refused.

## 4. Refusal shape

An identity in `removed` with no matching disposition is a typed, located, counted refusal — `cause=FloorExpectedRedUndispositionedShrink`, one line per identity up to a cap plus a count, mirroring `refuse_frozen_path_deferral_additions`'s own message shape (§5's "no absorbing fallback": the arm never widens or waves the row through, and there is no environment-variable or flag escape hatch, matching the freeze gate's own no-fallback discipline). The message names the three legitimate paths (still-passing evidence, corpus deletion, or a named Superseded row) so the failure is actionable rather than merely blocking.

## 5b. Three corrections from external review (sharp-raven-273, post-#8469) — resolved

Sections 1–4 above are the original note as published in #8469. External review found three real gaps, investigated below; §§5b.1–5b.2 fold cleanly back into Layers A/B, §5b.3 does not and is reported as a distinct finding rather than stretched to fit.

### 5b.1 — Correction 1: the baseline must be the computed transition, not today's count

Treating the current roster (358, or whatever `#8472` lands it at) as a clean starting point would silently ratify the 469→358 shrink — including the wrongly-dropped identities from `#8437` — as axiomatically legitimate the moment the gate goes live. That is exactly the failure this contract exists to prevent, applied to its own bootstrap.

**Resolution:** the gate's first baseline is not "today," it is the *computed* delta between #8457's base (`2c65eea`) and its merge (`6f3d374`), run once through Layers A+B below as a backfill, not asserted from the incident review's memory. Concretely: Layer A git-diffs `floor_expected_red.dag`'s roster text at those two refs (cheap, the same `git show`-based primitive the freeze gate already uses); every removed identity is then run through Layer B against *current* corpus/roster state (decl-scan for Retired, current-run pass evidence for Repaid, membership in the other declared rosters for the new arm in §5b.2). Where the computed disposition disagrees with the incident review's manual 164/28/5 split, the computed answer wins — this is the mechanical check the manual review stood in for, not a second opinion beside it. Going-forward monotonicity is then anchored at the *backfilled, dispositioned* state, never at an un-audited snapshot of the present.

### 5b.2 — Correction 2: renames need a declared succession arm, and it feeds a real Layer-B gap

`#8457` renamed modules. Under Layer A's plain `removed`/`added` set subtraction, a rename reads as an unrelated deletion plus an unrelated addition; under Layer B's original three dispositions, the removed (old) identity is neither Retired (its *decl* still resolves — under a new name) nor Repaid (the *old* qualified name never runs again), so it would incorrectly refuse or incorrectly fall to Retired depending on how the decl-scan is keyed.

**Resolution:** add `WitnessRenamed { old_identity, new_identity }` as a fourth Layer-B disposition, checked before Retired/Repaid. Per DESIGN §4 ("a heuristic is never necessary in a closed system") this must not be *inferred* from git's content-similarity rename detection — that is the same inference the keying-relation open thread already rejects for the fleet-reconcile lane. It is a **declared** row, gated the same way Superseded already is: an externally-observed fact (reviewer/operator-asserted pairing bound to the PR), not self-authored by the diff that performs the rename. A `WitnessRenamed` row is admitted only if `new_identity` is currently discovered-and-passing (or currently enrolled with the same or lesser severity) — a "rename" that lands on a deleted or newly-failing target is not a rename, it is a Retired-plus-new-failure and must refuse until dispositioned as such.

This also fixes a real hole `#5b.3`'s numbers exposed: some of the 111 roster-enrolled removals in `#8457` were not simple drops, they moved into `witness_deferral_freeze`'s own roster or `gunbc.explicit_witness_admission` (the "budget_refused pre-quarantine" and "tipped" identities sharp-raven's accounting names). Layer B's original Retired check (decl-scan only) cannot see that — a decl that still resolves but is now legitimately long-quarantined is neither Retired nor Repaid under the original three arms. **Add a fifth arm, `LongQuarantined { roster }`: the identity is currently a member of `witness_deferral_freeze`'s roster or `gunbc.explicit_witness_admission`.** This is cheap (a second small-text-roster membership check, same cost class as the rest of Layer B) and it is the correct, narrow generalization of "check the other declared rosters" that Correction 3 was gesturing at — see below for why it does not need to go further than this.

### 5b.3 — Correction 3: the whole offered set is a different, larger mechanism — not an instantiation of the freeze gate

The measured number, from sharp-raven-273's follow-up: `#8457` relocated 38 modules carrying 429 `test fn` declarations. 111 were `floor_expected_red` roster members (the 469→358 delta); 111 more were budget-refused/failing-but-never-enrolled; **207 — 48% of the affected population — were healthy witnesses enrolled nowhere.** That is the concrete proof that a wall scoped to roster membership is structurally blind to nearly half of what actually stopped executing: those 207 have no roster row to lose, so no roster-diff, however carefully dispositioned, can ever see them leave.

The candidate framing on the table is `offered = executed ∪ long ∪ live`, a disposition map `WitnessIdentity -> Executed | LongDeclined | LiveDeclined` computed per witness, diffed run-over-run. I traced how the floor actually computes each of those three today (`cli_run.rs`):

- **Executed** — `DiscoveryRow`, built by `invoke_floor_discovery_producer_over_corpus` (walking `*_test.dag` files under the configured scan dirs, judged live against the current corpus tree).
- **LongDeclined** — `DeferredDiscoveryRow`, built by `collect_deferred_discovery_rows` (same corpus walk, filtered through `witness_exclusion_substrings`/`witness_exclusion_frontier_rows`, tagged with an `exclude_reason`).
- **LiveDeclined** — `floor_expected_red_roster`, a hand-authored text roster, joined against this run's `ClaimOutcome`s inside `run_required_floor`.

The identity *type* is not the blocker — `WitnessIdentity{module_path, function}` / `witness_identity_qualified_name` (`floor2_prepared_subject.dag`) already unifies `module.function` across all three, and floor_expected_red rows are already qualified names in that shape. What blocks the reuse is **cost and artifact shape**, not naming:

`witness_deferral_freeze`'s and `floor_expected_red`'s git-diff layer is cheap *because the baseline is a single hand-authored text file*, comparable via `git show <ref>:<path>` — an O(1) tree read, no corpus walk. `Executed` and `LongDeclined` are not authored artifacts at all; they are *live-computed* every run by walking the whole `*_test.dag` corpus (`build_module_graph_facts_live`, `discover_owned_data_decls`, the discovery producer). There is no committed text to `git show` at an arbitrary historical ref for "what was executed at commit B" — answering that requires checking out commit B's full tree and *re-running discovery against it*, a full corpus walk per baseline resolution. That is precisely the cost-shape class DESIGN.md's 2026-08-11 deletion (the inert-lens/construction-justification censuses, killed for exactly this reason: "every discovery run... had to acquire a whole-corpus module graph in order to answer a question") already ruled out as a routine per-run cost, and adopting it silently here would be the same mistake at the opposite polarity.

The honest fix for the whole-offered-set case is not "diff two commits," it is **diff two *runs*': persist the discovery roster (`Executed ∪ LongDeclined ∪ LiveDeclined`, identity-grain) as a durable receipt each green run, and compare this run's computed roster against the last persisted one.** That is a real, valuable mechanism — it is the one that would have caught all 429 affected declarations in `#8437`/`#8457`, not just the 111 that happened to touch `floor_expected_red` — but it is **a different mechanism from `witness_deferral_freeze`, not an instantiation of it**: run-over-run receipt diffing, not two-commit text diffing. Reusing `collect_frozen_path_deferral_additions_for`'s git-diff core buys nothing here because the thing being diffed is not git history.

**Verdict, stated plainly per the standing instruction: it does not generalize as "the same mechanism," and I am saying so rather than stretching it.** §§5b.1–5b.2 above are real, cheap, in-scope strengthenings of the roster-membership wall this work item was scoped to build, and they should land. The 207/429 finding is real and is worth acting on as its own future work item — but **that item is not "build `gunbc.discovery_roster_ledger`."** Checking before proposing a new authority (DESIGN §3): `src/v1/stage0/src/cli_run/floor_discovery_snapshot.rs` already implements most of what a run-over-run ledger needs. `FloorDiscoverySnapshot` materializes the discovery roster (`DiscoveryRowSnapshot { label, entry, function, reads_live_tree }`) plus `request_identity_digest`, `roster_digest`, `payload_digest`, and `FloorDiscoveryTerminalReceipt` carries `tested_commit` / `tested_tree` / `walk_attempt_id`. That is the identity-grain, digested, commit-stamped roster the offered-set ledger needs — already built, not hypothetical.

What is actually missing, checked rather than assumed: (1) **retention** — the snapshot is written to `target/floor-attempts/floor-discovery-snapshot.json`; `target/` is repo-gitignored (`.gitignore:7`), and a grep of every `.github/workflows/*.yml` for `upload-artifact` finds it used only in `fleet-converge.yml`, never naming `floor-attempts` or `floor-discovery-snapshot` — nothing uploads or otherwise retains this file across a run today, so it does not survive to be diffed against a later run. (2) **the roster CONTENT has no consumer, though the artifact does have a live cross-process reader** — correction to an earlier overstatement in this note (sharp-raven-273, per-file header vs. per-caller check): `claim_executor.rs` calls `verify_floor_discovery_terminal_for_coordinator` (bin/claim_executor.rs:10000), which `fs::read_to_string`s *both* the `.terminal` receipt and the `.json` payload, deserializes the full `FloorDiscoverySnapshot` (including `snapshot.roster`), and cross-checks `request_identity_digest`/`payload_digest`/`tested_commit`/`tested_tree` with typed `Err` on any mismatch — that is a real, exercised-every-run cross-process read, for integrity, not the roster-walk-warming consumer the file's header documents deleting. What is genuinely absent is any caller that reads `snapshot.roster` *as data* — `verify_floor_discovery_terminal_for_coordinator` parses it only to digest-verify it, then discards it (`install_floor_discovery_snapshot`, the one place `snapshot.roster` becomes `DiscoveryRow`s again, has no caller in this tree). So "write-only" was too strong; the accurate statement is *the roster field has no content consumer*, while the artifact itself, its digests, and its commit/tree stamp are already read, verified, and refused-on-mismatch cross-process every run. (3) **coverage** — `DiscoveryRowSnapshot` mirrors `DiscoveryRow`, i.e. the *Executed* set only; it does not yet carry `LongDeclined`/`LiveDeclined` rows, so covering the full 429-declaration offered set needs those added to the snapshot shape, not a parallel carrier.

The corrected future work item, then, is **"persist and diff the existing `FloorDiscoverySnapshot`,"** not "build a new ledger authority" — and it is cheaper than a first reading suggests, because the hard part of a run-over-run diff (proving two snapshots describe the same subject, via digest cross-check) is already built and already exercised by `verify_floor_discovery_terminal_for_coordinator`: (a) give the snapshot real retention (a CI artifact upload, or a committed/pushed last-green receipt — a choice for that item, not this one); (b) extend `DiscoveryRowSnapshot`'s coverage to `LongDeclined` and `LiveDeclined` alongside `Executed`, closing the reused-carrier version of the 207/429 gap; (c) add a consumer of `snapshot.roster`'s *content* — comparing this run's roster against the retained prior snapshot's roster — reusing the coordinator's existing digest-coherence check rather than inventing a second one. Proposing a fresh `gunbc.discovery_roster_ledger` authority here, when this substrate already covers the identity/digest/commit-stamp half of the problem *and* has a live, exercised cross-process reader for it, would itself be the §3 second-authority mistake this whole lane exists to avoid — the same mistake this correction (Correction 3) was raised to prevent at the roster-membership layer. I am not building any of (a)–(c) here; they remain future work, now named against the real carrier and its real, narrower gap.

**On the module-path-index billing note:** Repaid/Retired/LongQuarantined/WitnessRenamed are all outcome-classifications (did it run, did it pass, is it in another declared roster, was it declared renamed) — none of them inspect *why* a run was slow or *where* a shared cache fill landed, so the "quarantined for being slow when the bill was actually relocated" failure mode sharp-raven flagged cannot leak into this vocabulary; a witness whose bill landed on it and blew budget is `BudgetRefused` today regardless of cause, and this design does not add a cause-sensitive arm.

## 5. Open, and explicitly not decided by this note

- **Superseded's typed carrier.** Candidate shape: a small roster analogous to `gunbc.explicit_witness_admission`, naming `{identity, new_home_or_authority, reason}`, gated the same way dissolution approvals already are — an externally-observed operator verdict bound to the current head, not a field the removing PR authors itself. Whether this is a new module or an extension of an existing disposition carrier (`gunbc.replacement_cut`'s `ConsumerDisposition` shape is a plausible sibling) is unresolved and should be settled by review before code lands.
- **Where Layer B's correlation actually executes.** Two placements are viable: (a) inside `run_required_floor` itself, since it already computes per-claim outcomes and already has the `stale_quarantine`/`expected_red_arm` machinery this reuses; or (b) as a separate post-run step over a receipt `run_required_floor` emits. (a) avoids inventing a new receipt format but couples the diff-baseline read into the floor's hot path; (b) keeps the floor unchanged but requires a durable per-run receipt of discovered identities and outcomes to exist for the correlation to consume. This note does not choose between them.
- **Cost.** Layer A's baseline resolution is git plumbing (cheap, same shape as the freeze gate). Layer B's decl-scan for Retired is the same bounded, per-entry file read the freeze gate already performs for its stale check — not a corpus-wide module-graph walk, so it does not reintroduce the cost-shape defect that got the inert-lens/construction-justification censuses deleted 2026-08-11. This should be confirmed against the actual identity counts once implemented, not assumed.
