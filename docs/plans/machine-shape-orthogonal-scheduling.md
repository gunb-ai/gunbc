## 1. The two design axioms

**A. Machine shape is data — and there is no machine *kind*.** One scheduling kernel; machine shapes are rows — never two schedulers (the §4 N×M-adapter trap). Stronger (operator directive, 2026-07-15): "CPU vs GPU" is not a modeled distinction, the same way "batch vs streaming" is not — a nickname pair for points on shared axes (§3). No `MachineKind = Cpu | Gpu` discriminant may exist, and no `match` over one can, because the types carry no such field — the fork is unwritable by construction (§5), not merely discouraged. Every scheduling difference must *emerge* from faithful facts:

- **"serial folds are bad on GPUs"** derives as idle-lane cost — a loop-carried dependency utilizes 1 of `lane_count` lanes; at `lane_count = 1` the *same formula* says the serial fold wastes nothing. A scalar core, a SIMD core (8–16 lanes), and a GPU SM cluster (thousands) are three fills of one axis, and the schedule's response is monotone in it — no threshold, no kind test.
- **"transfer cost to the device"** derives as interconnect-crossing in the machine graph — and vanishes *by topology* on unified-memory shapes (the cited `apple_m5` row shares the DRAM level between execution domains), never by a special case. A discrete card and an integrated one are two topologies of one model.
- **"batch vs streaming"** is already dissolved by the substrate's bounded-and-forward execution: everything is a fold over a bounded prefix; residency windows (`transfer_grain`) express streaming without a second mode.

The orthogonality claim: computation graph × machine facts × algebraic evidence → schedule, each axis independently variable, no cross-term hand-authored.

**B. Machine shape is definite allocation-as-contract (operator-signed reframe 2026-07-16).** The scheduler consumes a **bound, definite grant** — never per-value epistemics. Two sides, both already modeled: *description* = extdeps catalog rows (cited; genuinely ranged facts resolve at citation time into named single-valued fields — precedent: `CpuModelCatalogRow.nominal_sustained_per_thread_hz`, extdeps/cpu/types.dag:34, with deployment-observed values on a separate axis); *grant* = `compute_fabric`'s `Bound` (`Program` + `Opportunity.offers` + `connect`). Ungranted facts are **structurally absent** (a level not in the tower), never an `UnknownQuantity` value. **`Option` on a shape field means exactly one thing — the grant does not include this fact** (structural absence at field grain); consumers refuse / return `PricingRefused`, never default — the license for `transfer_grain?` / `bandwidth?` / `latency?`. Measurement receipts (`MeasuredBy`) stay in the witness-realization lane and are **unrepresentable in shapes** — no constructor admits them. A coarse grant (single domain, shallow tower) is legal to schedule; pricing refuses (`PricingRefused{missing}`) exactly where the grant structurally lacks a fact, counted.

## 2. The end shape (terminal model — operator agreement requested, then held fixed)

Operator working ruling (2026-07-15): define the end shape immediately, agree on the target, then move toward it in stages — no axis deferred into vagueness. The carrier types live in §3's block (they land in Phase 1); this section fixes the *semantics* — the laws every later phase moves toward. The movement is staged; the target is not.

- **Locality and latency are two axes, not one lattice (revised 2026-07-15 per review — the fused `LocalityTier` total order was wrong twice: `cache_interface` deliberately carries locality and latency as *separate* fields, cache_interface.dag:124-140, and `DeviceLocal` vs `InProcess` has no universal order — a level's nearness is relative to the consuming execution domain).** End state: (a) **latency** is a per-level magnitude — `MemoryLevel.latency: Nanosecond?` (optional = structurally absent from grant) — with ONE std latency-class *projection* converging the existing two-way class fork (`ReadLatencyClass = InProcessNs|LocalDiskUs|LanMs|WanTensMs`, cache_interface.dag:41; `LatencyClass = UltraLow|Low|Medium|High`, product/network_topology.dag:21) — the lift-out converges both class enums, never becomes a third; (b) **locality** is *graph-derived and domain-relative* — a level's position relative to a consuming domain is computed from `MachineShape` structure (tower order within a domain; edges crossed between domains), exactly as `sharing` already derives from `SharedLevelEdge` membership — never a stored universal enum. `cache_interface`'s monotone law (`cache_layer_ids_respect_locality`) survives as a law over each domain's *derived* ordering. Register file to WAN, one concept — but one *derived axis*, not one stored order (§2 horizontal).
- **Lockstep is structure; divergence is a derived price.** `LaneGrouping = IndependentLanes | Lockstep { group_width: HardwareThreadCount }`. The divergence law: within a `Lockstep` group, branch arms *serialize* (cost = sum of arms, lanes masked); across `IndependentLanes`, concurrent arms cost max. SIMD masking and SIMT warp divergence are this one law at two fills — a `gpu_divergence` special case cannot exist. The already-modeled PTX rows (`ThreadHierarchyShape`, `PtxCost` — `src/v2/extdeps/languages/ptx.dag`, today zero consumers) become concrete fills, gaining their consumer.
- **Idle-lane law.** A loop-carried dependency occupies 1 of `lane_count` lanes; idle cost is derived and monotone in `lane_count`. "Serial folds are bad on wide machines" is this law's high-fill reading; at `lane_count = 1` the same law prices the waste at zero.
- **Crossing law.** Transfer cost is a property of the `InterconnectEdge` crossed — `LinkEdge` prices by link bandwidth/latency; `SharedLevelEdge` crossings price as ordinary tower traffic on the shared level (zero link cost). Unified vs discrete is topology, never a mode.
- **Placement's terminal state.** `Placement` dissolves into a `DomainId` — a *reference to an `ExecutionDomain` in the machine graph*, a position, never a kind (representable because domains carry stable identities — §3 type block, revised per review). `LocalAccelerator` is acknowledged as a smuggled kind (operator ruling 2026-07-15: added recently, "needs to keep being scrutinized"); retained during migration under the coarse-tier reading, with this dissolution as its named trigger (§6 discipline: scaffold + trigger, never a silent survivor).
- **Kind-erasure at the derivation boundary.** Cited catalog layers *keep* their upstream kinds — `ProcessorKind = CpuProcessor|GpuProcessor|AcceleratorProcessor` (fleet_intent.dag) and `MemoryKind = Dram|Hbm|UnifiedShared` (extdeps/memory/types.dag:18) are §3-faithful where vendors publish those families — but the `ComputeHost → MachineShape` derivation **erases** them: the scheduler's view carries facts only. One catalog row flagged for the same scrutiny as `LocalAccelerator`: `MemoryKind.UnifiedShared` fuses a *topology* fact (who can address it) into a *technology* enum (`Dram`/`Hbm` are silicon; an M5's "unified" memory is technologically LPDDR that happens to be shared) — the end shape derives unified-ness from `SharedLevelEdge` and the enum should shed that variant when the graph carrier lands.
- **The one-derivation law.** `schedule = derive(computation_graph × machine_facts × algebraic_evidence)`. Any difference between two machines' schedules must be traceable to a fact difference. This wall is judgment-guarded for now (§9, ruling 4) — held in operator review until a mechanical guardian exists.

## 3. Phase 1 — model the machine shape (std + extdeps; no scheduler change)

New std authority (`std.machine_shape`) — **import-clean** (std never imports extdeps; derivations live beside their cited rows in extdeps/, cross-domain composition in product/):

```
type DomainId = NonEmptyStr where brand("DomainId")
type LevelId  = NonEmptyStr where brand("LevelId")
type MemoryLevel {
  id:             LevelId
  capacity:       ByteSize
  transfer_grain: ByteSize?      -- absent = structurally ungranted
  bandwidth:      Bandwidth?
  latency:        Nanosecond?
}
type MemoryShape = List<MemoryLevel>
type LaneGrouping = IndependentLanes | Lockstep { group_width: HardwareThreadCount }
type ExecutionShape { lane_count: HardwareThreadCount, grouping: LaneGrouping }
type ExecutionDomain { id: DomainId, execution: ExecutionShape, memory: MemoryShape }
type InterconnectLink { bandwidth: Bandwidth, latency: Nanosecond? }   -- agnostic link facts (magnitude, not enum); PCIe/network dispatch lives in extdeps
type InterconnectEdge
  = LinkEdge        { from: DomainId, to: DomainId, link: InterconnectLink }
  | SharedLevelEdge { owner: DomainId, sharer: DomainId, level: LevelId }
type MachineShape { domains: List<ExecutionDomain>, edges: List<InterconnectEdge> }
```

Extdeps derivations (beside their rows): `extdeps.gpu.machine_shape.shape_from_catalog` (GPU catalog → single-domain grant); `extdeps.storage.types.pcie_interconnect_link` (reuses `pcie_link_bandwidth` — derived, never stored). Cross-domain host composition, when it comes, lives in `product/` (precedent: hardware_selection composes cpu+memory rows).

**No `Quantified<T>`, no `UnknownQuantity`, no per-value `Evidence` on shapes.** Measurement receipts stay in witness-realization; topology = pure fn(graph × bound shape).

A host is a *graph* of execution domains whose memory towers may share levels — and it is now literally representable as one: domains and levels carry stable identities, edges carry endpoints, and §2's terminal `Placement` is a `DomainId` reference. "Where a computation runs" is a domain in this graph; "what a move costs" is the edge it crosses (zero link-edges crossed = zero transfer, emerging on unified-memory shapes with no special case). There is deliberately no field that names what a domain *is* — only what it *has*.

## 4. Phase 2 — operand facts on edges (the crux the survey located)

Today `DependencyView` edges carry no operand: the scheduler collapses `DataDependsOn` to a Bool (`src/v2/workflow/scheduler.dag:55-73`), so shared-operand structure — N consumers of one value — is invisible to batch formation. Locality is a property of *edges* (data flowing), not nodes; this phase gives it a carrier.

- **Total derivation, spelled out (revised per review: the original row assumed identities that do not exist yet — `DependencyView` carries no operand, dependency.dag:36-41).** Three defined pieces, each fail-closed:
  1. *Operand identity* = the producer's output value-root: `operand_root(edge: DependencyView) -> OperandRoot { root: Node } | OperandRootUnresolved { edge }` — defined for `DataDependsOn` as the source node's materialized output binding; every other `DependencyKind` carries no operand by construction; an unresolvable producer output refuses, never guesses.
  2. *One hash authority, as a precondition*: `materialize` keys on `v2.std.node.Hash` (materialize.dag:3,13) while the plan layer carries `ContentHash` (`RealizationPlan.target`) — the same fnv1a64 dual-surface §3 thread DESIGN.md already tracks. `OperandFlow` is **gated on grounding these as one authority**; landing it across two hash carriers would cement the fork this lane exists to prevent.
  3. *Footprint* binds to `node_keyed_graph_transitive_bytes` (`realization_runner.dag:60`: "transitive footprint is DERIVED, never stored... no parallel size walk may exist anywhere") **via the node-keyed artifact/root mapping that fn requires (realization_runner.dag:174-182)** — the edge→root mapping of (1) is exactly that missing input; a second size walk is a hard reject; `NodeKeyedGraphTransitiveBytesUnsettled` surfaces as a refused row.

  Result rows: `OperandFlow { edge, operand, footprint: ByteSize } | OperandFlowRefused { edge, cause }` — refused rows are typed and counted, and produce no affinity claims downstream.
- The operand's `ContentHash` is the *same* identity `materialize` keys `Share` on — one identity, two schedule consequences: dedup (don't compute twice) and affinity (consumers run adjacent). This is the §3 unification that makes cache shaping fall out of machinery we already trust.
- Populate `CostAccount.space`'s **`DerivedFrom` fill only** (static operand footprint) from the same authority — discharging the declared P1 fill, **not** the AIMD governor's dissolve-on (#6663 review amendment 2): the governor packs against *measured per-runnable peak*, a different space fact — receipt: the whole-corpus run peaked at 6.25 GB VmSize while operand data was kilobytes; the mass was retention, not operands (the v1 run-stability throughline's exact axis). The dissolve-on additionally requires `MeasuredBy` peaks (witness-realization P1, #6663). The Evidence split expresses the distinction — `DerivedFrom` footprint vs `MeasuredBy` peak — never conflate them.

Acceptance: for a fixture graph with one Substantial shared operand and two consumers, the derived `OperandFlow` rows name the same `ContentHash` with equal derived footprints; RED: a graph whose footprint is unsettled yields typed `OperandFlowRefused` rows and *no* affinity claim downstream.

## 5. Phase 3 — locality: affinity as derived topology (every level of the tower, any machine)

The repel primitive exists (`runnable_excludes_corpus_co_residence` → `ResourceDependsOn` edges, `ci_floor_plan.dag:322-352`); the attract dual does not.

**Refinement, operator-ruled 2026-07-15 — dissolves the apparent conflict with the signed scheduling authority rather than superseding it.** The signed invariant's wording (`bounded-input-cost-envelope-scheduling.md:10-18`: topology hardware-free; `schedule_eq` across hosts) **conflated determinism with input-invariance** (operator: "if an A100 has more resources it's probably expected that the output is different"). Restated as three separate properties: (1) **determinism** — `topology = derive(computation_graph × declared MachineShape)` is a pure function: same inputs → same schedule, always, everywhere; (2) **the surviving wall: no UNSTABLE inputs to topology** — `MeasuredBy` quantities are banned because measured values vary run-to-run on *identical* inputs, which is what actually breaks reproducibility; a *declared* shape (`Cited`/`DerivedFrom`, content-addressed) is as stable an input as the source code itself; measured values stay peripheral (width, admission, the AIMD governor); (3) **cross-host `schedule_eq` is demoted from axiom to corollary** — it holds exactly when declared shapes are equal; a schedule that differs when its inputs differ is behaving, not flapping. The signed doc's invariant-4 wording receives a marked amendment to this restatement when this phase lands. (Composes cleanly with witness-realization P4, #6663: this plan prices *topology* from declared shape; P4 packs *width* from measured peaks — the same stable/unstable-input split, verified compatible by that review.)

- Rule (under the refinement): consumers of one `Share`d operand whose footprint is `Substantial` relative to a level's capacity prefer co-batch placement within that operand's residency window; where the readiness frontier permits multiple legal compositions, affinity selects deterministically among them.
- Pricing: a `TrafficAccount` per level boundary — bytes crossing each `MemoryLevel`, derived from schedule × OperandFlow × MachineShape; roofline `predicted_time = max(compute_time, traffic_i / bandwidth_i)`. Fused-vs-unfused kernels now price differently — the Phase-0 gap closes. **The pricer refuses, never degrades (revised per review — the earlier "term-incomplete `Predicted` account" was a §5 fallback answer: pricing that continues despite ignorance):** it returns `Priced { account } | PricingRefused { missing: List<QuantityRef> }`; a missing bandwidth or footprint yields `PricingRefused`, counted, and any comparison consuming a refused price is itself refused. No account with silent holes exists.
- Anti-goal (§4): no tunable knobs — no prefetch distances, no blocking factors, no thresholds. Every decision derives from (footprint vs capacity) comparisons over evidence-carrying quantities; absent evidence = a typed refusal, not a default.

Acceptance: a two-consumer shared-operand fixture schedules the consumers co-batch when capacity evidence admits both, with a `TrafficAccount` showing the operand loaded once; RED (discriminating): force the consumers into separate batches and the account shows the double load — the defect is *visible in the account*, which is the point.

## 6. Phase 4 — within-fold parallelization: licensed by algebraic evidence, priced by lane facts

A serial fold is optimal at `lane_count = 1` and leaves `lane_count − 1` lanes idle otherwise — one derived cost, no machine kinds. What licenses parallelizing *within* a fold (tree-reduce/scan) is associativity of the combine. MapReduce demands it by assertion; this substrate can demand it **by executed witness**.

**Ruling 11 supersedes this phase's staging (operator, 2026-07-16 — "do not introduce demo/concepts that break the main patterns of the repo, i.e. throwaway code"; first attempt #6727 closed unmerged).** The earlier "demo's contiguous-loop/SIMD path as first consumer" element is REJECTED: a demo landing hand-wires the very facts the real system must derive (combine/inhabitant/law refs as authored data rows, a hand-typed `ExecutionReceiptDigest` standing where an executed witness receipt must be — a forged license, fail-open in scaffold clothing) and grows the Rust seed for throwaway machinery. Phase 4 re-enters only when ALL of: (a) licenses are grantable exclusively from **executed** law-claim receipts (the witness-realization receipts lane) — a hand-authored receipt digest is unwritable-by-review anywhere, ever; (b) the first consumer is a **real corpus fold** (a reduction the tree actually runs), with carriers landing in the same PR as that consumer — no machinery without its real consumer; (c) the corpus-default state is the refusal path — `NotWitnessed → SerialFold`, priced with idle-lane cost — proven by RED before any grant exists. The GPU remains the same recognition with a larger fill — never a second path:

- **License verdict lattice (validated by the closed #6727 rework; binding for re-entry).** `associativity_license_verdict(evidence, scheduled_combine)` gates in order, fail-closed at every arm: (1) `NotWitnessed` → `Missing` → recognition refuses (`AssociativityNotWitnessedForFold`, serial baseline, idle-lane cost visible); (2) `evidence.combine` ≠ scheduled combine → `CombineMismatch`; (3) inhabitant ≠ the law's expected inhabitant → `SubjectMismatch` (the Nat-law-for-Int-combine case — for an Int combine the law authority is `claim_int_add_associativity` (Int inhabitant), never the Nat law); (4) receipt not from an **executed** law witness → `Missing`, never `Granted` (the gate reads real witness-realization receipts; a hand-authored digest is unwritable-by-review); (5) all gates pass → `Granted`, and only then may `derive_tree_reduce_parallelism` run — a degenerate geometry is `TreeReduceGeometryDegenerate`, its own typed refusal, not a silent serial fallback.
- **Law carrier — subject-bound, not a bare ref (revised per review: a lone `DeclarationRef` is forgeable — an unrelated law could license an unsound reduction).** The mechanism exists in two halves: law obligations consumed by testgen (`NatAlgebraLawObligation { algebra, inhabitant, law }` — note it already carries its *subject* fields, `src/v2/std/nat.dag:83-105`) and green-by-execution monoid law witnesses (`keyed_delta_fold_witness_test.dag:116-146` — cited as the *mechanism precedent only*: it proves `KeyedPatch` associativity and licenses nothing about any other combine). Commutativity is **never** required: structural order is preserved by the DependencyView/tree-reduce (Feinberg's commutative-monoid demand exists only because hash-shuffle destroys order; we never destroy order). Scope note resolving this phase's half of the §5-phase invariant question: within-fold expansion (serial vs tree-reduce) is realized *inside* the `RunnableKernelWorkload`'s kernel plan — like `fused_op_count`, a workload-internal fact — it never edits central `Schedule` topology.
- **Recognition fold grows one class.** `ElementwiseFoldClass` gains `AssociativeFoldChain { combine, evidence }` beside `PureElementwiseChain`; recognized → a tree-reduce/scan kernel plan whose depth/width derive from the target domain's `lane_count`; `NotWitnessed` → typed refusal (the fold stays serial — a correct schedule at any lane count, merely priced with its idle-lane cost so the displaced value of *witnessing* the law becomes visible). `DataDependentGather` stays `Refused` — the honest wall, unchanged.

## 7. The orthogonality proof (the DESIGN §7 deliverable)

One derivation, **three fills on one axis**, by execution: run the same computation graph (the demo's fused elementwise chain + one witnessed-associative reduction) through the one scheduling kernel against three `MachineShape` fills that differ only in facts — scalar domain (`lane_count: 1`, Ampere core), SIMD domain (`lane_count: ~8-16`, same tower), many-lane domain behind a `LinkEdge` (RTX 5090 fill, `lane_count: 21760`):

- the derived schedules are, respectively: serial fold / shallow tree-reduce / deep tree-reduce with priced edge-crossing — a **monotone response to `lane_count`**, with graph-independence parallelism and affinity batching identical across all three (those derive from the computation graph and memory tower, not the lanes);
- a fourth fill — same many-lane domain joined by `SharedLevelEdge` instead (the `apple_m5` topology) — prices crossing at zero and the placement flips accordingly, *with no code path knowing it is "integrated"*;
- all fills produce differential-equivalent results under their declared contracts;
- **discriminating REDs**: (i) strip the associativity witness → every fill degrades to the serial fold (never fabricates a parallel plan), and the idle-lane cost term makes the loss visible at high lane counts; (ii) a minimal grant (single domain, absent optional level facts) → still a *legal* schedule, no affinity/placement/pricing claims where facts are structurally absent — refusals counted; (iii) the kind-fork RED is discharged by construction — there is no discriminant to match on, so the forked-scheduler state is unwritable rather than tested-for.

That set of REDs *is* the orthogonality claim made executable: the schedule is a function of machine facts — monotone where the facts are ordered — and every cross-term is either derived or a typed refusal.
