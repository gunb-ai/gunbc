# gunbc-served dashboard + in-process dispatch (roadmap belt B)

Owner lane: `cool-wolf-720` (belt B) · parent: `royal-carp-451` (belt A interim) · operator direction 2026-07-20: dispatch is a **manual click** from the roadmap UI, one node at a time.

## The claim (and its consequence chain back to DESIGN)

The srv1 dashboard today is an **emitted JS program** (`node /opt/gunbc/server.js`, generated by `dag/gunbc/node_http_server_emit.dag`) that can only serve **static bodies frozen at emit time**, and the click-to-dispatch path built for it (belt A, in flight in the parent lane) has that Node process **exec a subprocess** (`env GUNBC_BELT_NODE_ID=<id> gunbc run --function belt_dispatch_node_cli`). That shape pays three avoidable costs:

- **§3 dual representation:** the served page is a snapshot of the roadmap authority, re-frozen on every deploy; the serving program is a second, emitted realization of "match method × path → respond" that the substrate already models (`ServedStaticRouteTable`).
- **shell → intent (DESIGN open thread):** the A dispatch path is a runtime-present site that still round-trips through an environment-variable channel + subprocess exec — exactly the class the routing correction says should be a typed in-process call when a gunbc runtime is on the path.
- **cost:** every dispatch pays a full CLI startup (load + compile + resolve of the source tree, ~seconds) per click; the serve process already paid it once.

**B's end state:** `gunbc-roadmap.service` runs **`gunbc serve`** — the seed binary itself is the HTTP server. `GET /` renders the roadmap page from the live authority; `POST /dispatch/<node_id>` calls `gunbc.roadmap_belt_actuate.belt_dispatch_node` **in-process** (no emitted JS, no subprocess, no smuggled program). A supersedes into B; the Node server + its emit lane retire when B is live on srv1.

## 1. Model: requests, responses, and a route sum with dynamic handlers

`extdeps/http/server.dag` (extends the existing module; RFC 9110 anchor already present):

```
type ServeHttpRequest {
  method: HttpMethod
  path: String            -- decoded path, query stripped by the host seam
  body: String
}

type ServeHttpResponse {
  status: HttpStatus
  content_type: HttpContentType
  body: String
}

type PathParamBinding { name: String, value: String }

type ServedRoute<H>
  = StaticRoute { route: ServedStaticRoute }
  | DynamicRoute { method: HttpMethod, path_pattern: PathTemplate, handler: H }

type ServedRouteTable<H> { routes: List<ServedRoute<H>> }

type RouteSelection<H>
  = SelectedStatic { route: ServedStaticRoute }
  | SelectedDynamic { handler: H, params: List<PathParamBinding> }
  | MethodNotAllowed { allowed: List<HttpMethod> }
  | NoRouteMatched
```

- `ServedStaticRoute` is **embedded**, not re-modeled — a static body is the degenerate handler (§2: one concept, every breadth). The generic `H` keeps the layer DAG strict: extdeps owns the route *shape*; it cannot and does not name gunbc's handlers (that would be an import arrow pointing the wrong way, the §3 dispatch-lives-peripheral rule).
- `serve_select_route(table, method, path) -> RouteSelection<H>` is a pure fold: first (method, template)-match wins; a path that matches some template under a different method folds to `MethodNotAllowed` with the allowed set (mirrors the emitted Node server's 405 semantics — same behavior, second realization of the same rows); nothing matched is `NoRouteMatched`. Selection is total — every arm is a value, no absorbing default.
- `extdeps/uri_path.dag` grows `match_path_template(template, path) -> PathTemplateMatch = PathMatched { params } | PathNotMatched` — segment-wise: `LiteralToken` must equal the segment, `ParamToken` binds it; segment-count mismatch is `PathNotMatched`. This is the forward reading of the very rows `emit_path_template_regex_source` reads backward.

**Invoke is not in extdeps.** A `RouteSelection` names a handler; *calling* it is the instantiation's job (dispatch sits peripheral, §3).

## 2. Handlers: the gunbc instantiation

New `dag/gunbc/roadmap_serve.dag`, `H = RoadmapServeHandler`:

```
type RoadmapServeHandler
  = BeltDispatchHandler        -- POST /dispatch/{node_id}
```

The route table = every row of `roadmap_dashboard_served_static_route_table()` lifted via `StaticRoute` (GET `/`, GET `/roadmap`, `/healthz`, `/ROADMAP.md`, `/target/roadmap-dispatch.json` — the page rows now carry the launch button + script, §4 below) **plus** one dynamic row: `DynamicRoute { method: POST, path_pattern: /dispatch/{node_id}, handler: BeltDispatchHandler }`.

Wait — static page rows frozen into the table would re-freeze the roadmap (the §3 cost this design exists to remove). So the page rows are **not** static rows here:

```
type RoadmapServeHandler
  = RoadmapDailyPageHandler    -- GET /
  | RoadmapFullPageHandler     -- GET /roadmap
  | DispatchJsonHandler        -- GET /target/roadmap-dispatch.json
  | RoadmapMdHandler           -- GET /ROADMAP.md
  | HealthzHandler             -- GET /healthz
  | BeltDispatchHandler        -- POST /dispatch/{node_id}
```

Every route row in the serve table is a `DynamicRoute` naming one of these; the handler bodies call the **same** authority functions the static-site artifacts call (`roadmap_daily_workspace_page_for_authority`, `roadmap_site_dispatch_json_body`, `expected_roadmap_md`, …) — the artifact table and the serve table are two projections of one set of authorities, not two copies of content. `ServedStaticRoute`/`StaticRoute` remains the right arm for genuinely emit-frozen consumers (the Node server keeps using it until it retires).

`roadmap_serve_invoke(handler, request, params) -> ServeHttpResponse`:

- page handlers → `try_serialize_html_source(page)`: `EmitOk` → 200 `TextHtmlUtf8`; `EmitRejected` → **500 with the typed reason** (never an empty page — the existing `EmitRejected => []` route-drop in `node_http_server_emit` is a silent widen this path does not copy).
- `DispatchJsonHandler` / `RoadmapMdHandler` / `HealthzHandler` → 200 with the existing bodies.
- `BeltDispatchHandler` → require param `node_id` (absent/empty → 400 typed — unreachable by construction from the template, kept as a typed refusal, not a fabricated dispatch); call `belt_dispatch_node(node_id)`; body = `serialize_json(belt_dispatch_result_json_value(r))`; status mapped **per variant, total**:
  - `DispatchSpawned`, `DispatchAlreadyLive` → 200 (idempotent click, same as the CLI's ExitSuccess)
  - `DispatchNodeNotFound` → 404
  - `DispatchNodeAlreadyDone` → 409
  - `DispatchObserveRefused` → 503 (the live set was unknowable; retryable)
  - `DispatchSpawnFailed` → 502 (actuation failed; receipt carries step + detail)

`roadmap_serve_handle(method: String, path: String, body: String) -> ServeWireResponse` is the single entry the host seam calls: parse the method label (unknown → 405 wire-style typed refusal), select, invoke, and project to the wire record `ServeWireResponse { status: Int, content_type_label: String, body: String }` (`HttpStatus`→Int, `http_content_type_wire_label`) so the Rust seam never touches a modeled enum.

## 3. The host seam: `gunbc serve` (seed execution mode)

New subcommand in the seed (`main.rs` dispatch + `cli_run::handle_serve`; both files are HAND_MAINTAINED roster members, and this is a new thin *handler* alongside `handle_run`/`handle_converge`, not census/index relocation — the #6046 gate class):

```
gunbc serve --source-root dag --source-root src/v2 \
  --entry dag/gunbc/roadmap_serve.dag --function roadmap_serve_handle \
  --host 127.0.0.1 --port 8080
```

- **Startup (once):** exactly `handle_run`'s load path — `load_sources_for_entry` → `compile_to_resolved` → blocking-diagnostic check → `InterpContext::new(…, ExecutionMode::Wet)`. Refuses (exit 1, diagnostics rendered) before binding the socket if the tree does not compile — a broken tree never serves.
- **Accept loop (thin):** `std::net::TcpListener`, **sequential** — one request at a time. This is a correctness choice, not laziness: `belt_dispatch_node` is idempotent by observe-before-spawn, and serializing requests makes the observe→spawn window race-free by construction (two concurrent clicks cannot both observe absent). The dashboard has one operator; throughput is not a requirement.
- **Per request:** minimal HTTP/1.1 read — request line (method, target; query stripped), headers only to find `Content-Length`, body read exactly to that length. Anything unparseable → 400 (typed one-line body), connection closed. No keep-alive, no chunked bodies, no TLS (tailscale serve terminates HTTPS in front, unchanged).
- **Call:** `run_in_context_with_args(ctx, function, [(method, Str), (path, Str), (body, Str)], …)`; read the returned `ServeWireResponse` record fields (the `classify_exit` pattern). `InterpError` → 500 with the error text; a non-record / wrong-shape return → 500 typed. The process stays up — one failed request is a counted loud response, not a crash (systemd `Restart=on-failure` still backstops a genuine crash).
- **No routing, no handler knowledge, no belt knowledge in Rust.** The seam is `(method, path, body) → (status, content_type, body)`, the same altitude as `WitnessBin.Run`'s argv seam.

**Interpreted-workload disposition (named, up front):** ROADMAP §④ rules a NEW long-running interpreted workload a review reject, routed through emit-on-demand. `gunbc serve` under the tree-walker is exactly that; it lands as a **declared Scaffold** (`std.disposition` row in `roadmap_serve.dag` binding the serve entry) with dissolution trigger = emit-on-demand of the serve closure (emit → build → run native, artifact shared by content-hash — the same lane as the S1 parse census). The per-request cost until then is bounded and honest: page render is a pure fold over the roadmap authority; the context is built once; and the §④ ledger for server loops ("declared-emergent frames obligate up front") is satisfied by this row. The displaced cost that justifies interim interpretation: A's per-click CLI startup (full load+compile per dispatch) is *worse* than B's one-time startup, so B is a strict cost improvement even before emit-on-demand.

## 4. Page: launch buttons + client script — **A's, inherited** (lane split, parent 2026-07-20)

The launch button + minimal client script land in `gunbc.roadmap_page` in **belt A** (parent lane royal-carp-451); B does **not** edit the page and rebases on A's merge. The agreed seam: the button is **transport-agnostic** — it POSTs to `/dispatch/{node_id}`, and both A (Node server exec route, interim) and B (`gunbc serve` in-process) answer that same path. The page never knows which backend answered, so B swaps under it with zero page change. B's serve table renders whatever `roadmap_page` produces at request time — the button arrives in B automatically when A merges.

(The `std.markup` escaping wall — all text HTML-escaped, no raw arm, so script text must be authored escape-free — is therefore A's to guard at authoring time; the raw-text-element modeling of `script`/`style` per HTML5 remains the named grounded fix for whoever hits it first, deliberately not in this PR.)

## 5. Deploy: the members change, the spine does not

`gunbc.live_deploy.spec` today: members = {tailscale pkg, nodejs pkg (Ensured), server.js, systemd unit, tailscale-serve (Owned)}. B's desired membership:

- **New single authority `dag/gunbc/host_layout.dag`** (`gunbc.host_layout`): `srv1_gunbc_repo_root = /opt/gunbc/gunbc`, `srv1_gunbc_serve_binary = /opt/gunbc/bin/gunbc`, `srv1_dispatch_worktree_root = /opt/gunbc/dispatch-worktrees`. `roadmap_belt_actuate.belt_actuate_workdir` AND `roadmap_dispatch_actuator.dispatch_worktree_root` re-ground as projections of these rows (deleting their private copies — the belt spawn root and the serve tree are **the same fact**, which is precisely why dispatch works in-process: the serving tree is the repo the belt worktrees from). The deploy spec and the systemd unit consume the same rows. Lane agreement (parent 2026-07-20): A provisions srv1 **manually to these exact paths** for the interim (no env-var fork, no .dag path change on A's side), so the baked defaults work today; B's PR formalizes that same provisioning through the deploy membership — after B's apply, the paths exist *because the deploy's own membership says so*, and the interim hand-provisioning retires.
- **Members:** `ServeBinary` (Owned, path `srv1_gunbc_serve_binary`; upsert = `sudo install -m 0755` of the deploy job's built seed binary — the deploy job already builds the seed to run `gunbc run --function live_deploy_apply_srv1_wet`, so the artifact is present by construction), `GunbcSourceTree` (Owned, path `srv1_gunbc_repo_root`; upsert = rsync of the runner checkout **including `.git`** — the belt's `git worktree add` requires a real repo), `SystemdUnit` (ExecStart flips to `gunbc serve …` per §3, `WorkingDirectory` = repo root), `TailscaleServeMapping` (unchanged), `TmuxPackage` (Ensured — the belt's observe/spawn substrate; today present by hand). `NodeJsPackage` and `ServerScript` leave the desired set — under the membership poles that is exactly a `Removed → Teardown` for the Owned server.js and **no teardown** for the Ensured nodejs (R5: Ensured is never torn down — the wall already in the spine). The `claude` CLI is deliberately NOT a member this PR (hand-present on srv1; a follow-up models its provisioning honestly rather than smuggling a curl|bash).
- The apply/retract scripts + systemd unit goldens regenerate through the existing `emit.dag` pipeline (`orch_emit_pipeline` over the bash medium); the committed `.github/live-deploy-srv1-apply.sh`/`-retract.sh` drift gates stay the byte oracles. The `install_d_shared_setup_latent_coupling_note` marker fires by design: a second (and third) `/opt/gunbc` writer arrives, so the `install -d` moves to the shared-prefix form the note prescribes.
- Readiness/digest read-back (`live_deploy.readiness`, `roadmap_static_site` digest): unchanged consumers — `/healthz` and the served-digest read-back now prove the **gunbc-served** process. The digest artifact remains content-addressed over the *body*, so the read-back is server-implementation-agnostic by construction (the receipt that proves A→B preserved the contract).

Deploy risk containment: the flip is one systemd unit + two new members; retract restores by the same poles; and the belt A path (Node + exec) remains reachable on the parent's branch if rollback is needed — rollback = revert the spec members, regen goldens.

## 6. Proof by execution

**Witness suite** (`dag/test/claim/roadmap_serve_witness_test.dag` + extensions to `node_http_server_emit_test.dag`):

- `match_path_template`: literal hit · param binding extraction (`/dispatch/abc` → `node_id=abc`) · segment-count miss · literal miss (each a separate witness; the miss cases are the REDs).
- `serve_select_route`: GET `/` selects the daily page handler · POST `/dispatch/x` selects `BeltDispatchHandler` with the param bound · GET `/dispatch/x` → `MethodNotAllowed [POST]` · unknown path → `NoRouteMatched` · first-match-wins on an overlapping table (discriminating input).
- status mapping totality: every `BeltDispatchResult` variant → its status row (6 witnesses; the 409/503/502 arms are the REDs that a lazy 200-or-500 collapse would fail).
- page: a not-signed-off fixture node renders the `data-dispatch` button; a signed-off node renders none; the script guard witness — the live script passes `escape_text(js) == js`, and a perturbed script containing `&&` **refuses** (the RED that keeps the wall live).
- goldens: server.js + apply/retract scripts + systemd unit re-frozen; drift gates stay the byte oracles.

**Seed-side receipts (documented in the PR, run by execution):**

1. Local: `gunbc serve` on a scratch port → `curl GET /` returns the page containing `data-dispatch` buttons; `curl -X POST /dispatch/<unknown>` → 404 + typed JSON (RED); with a fake `claude`/`tmux` on PATH (the parent's fake-worker pattern) `POST /dispatch/<real-open-node>` → 200 spawned, immediate second POST → 200 `already_live` and **no** second `tmux new-session` (idempotency by execution).
2. srv1 (ssh): same binary + tree under the real host; `GET /` receipt; dispatch receipt against a disposable node. The systemd/tailscale flip itself lands via the deploy stage on merge (`live_deploy_apply_srv1_wet`), whose readiness + digest read-back is the independent proof.

## Non-goals (named)

- No TLS/auth in `gunbc serve` (tailscale serve fronts it, unchanged; the tailnet is the auth boundary today).
- No concurrent request handling, keep-alive, or streaming — sequential by design (see §3).
- No autonomous belt tick from the server (`belt_run_once` stays CLI/timer-driven; the server only exposes the manual click).
- No `claude` CLI provisioning member (hand-present; follow-up).
- No raw-text-element modeling in `std.markup` this PR (named dissolution of the script guard).
- The Node-server emit lane (`node_http_server_emit`) is not deleted here — it retires when B is live on srv1 and the parent signs A's supersession; its dissolution trigger is this design.
