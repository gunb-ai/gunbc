## Capability, and why rootless

The brief names the shape: rootless Docker for `ghrunner`, plus the NVIDIA container
toolkit with a CDI spec, so `docker run --device nvidia.com/gpu=all` works.

- srv1 has rootful docker, but putting `ghrunner` in the `docker` group is root
  equivalence — the docker socket is the root socket. That is RULED OUT.
- srv1 measured facts already satisfy the rootless shape: `docker-ce-rootless-extras`
  29.7.2, `nvidia-container-toolkit` 1.20.1-1, `nvidia-ctk`, `/etc/cdi/nvidia.yaml`,
  ghrunner's rootless daemon running at `/run/user/999/docker.sock` with `Linger=yes`.
- srv3 has NEITHER docker NOR the container toolkit (measured below).

The runner unit already carries the rootless endpoint: `runner_unit_file.dag`
`docker_host_from_uid_reading` forms `DOCKER_HOST` from the job user's uid via
`docker_rootless_unix_endpoint(uid:)`, i.e. `unix:///run/user/<uid>/docker.sock`. So the
model already assumes rootless; the gap is that nothing declares or ensures the packages.

  `ghrunner:100000:65536` and `ubuntu:100000:65536` — the two ranges OVERLAP. Same

  but it is a real modeling gap: nothing in `.dag` declares subuid/subgid allocation

  map the same subordinate ids, so a container writing as subordinate uid 100000 can be
  read by the other user's mapping. Declaring the ranges per host, distinct, is part of
  this work.
