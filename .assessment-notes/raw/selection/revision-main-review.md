# Review of logical-work-revision-main.md

Reviewed 2026-10-23 against source HEAD `7daaddd1f0ce99734e1ddb57138313701455c758`, the parent's R2–R10 requirements, and the previously supplied storage/lifecycle audits. R1 population completeness is deliberately excluded from this review. No repository edits, builds, tests or live effects were performed.

## Blocking factual correction

**F1 — Section 4 conflates durable holds with expiring temporal leases.** The row says ownership, expected revision, expiry and monotonic fencing must guard every protected effect, citing both `std.durable_exclusive_hold` and `std.temporal_effect::HeldLease`. Those authorities deliberately differ. `std.durable_exclusive_hold::durable_hold_recovery_assess` has no clock or expiry and permits recovery only with a holder-bound, acquisition-generation-bound `HolderObservedDead` report. Its comments explicitly reject a declared lease deadline as evidence of death. `durable_hold_release_assess` also checks both owner and acquisition generation to refuse ABA release. `std.temporal_effect::held_lease_observed_verdict` instead distinguishes `LeaseRunningPastExpiry`, and `decision_for_held_lease_verdict` maps that to drain-then-start. The proposed universal expiry requirement changes an existing hold law rather than preserving it.

Correction: split the row, or state “Preserve hold occupancy, owner/acquisition-generation fencing and observed-death recovery; preserve the distinct temporal-lease expiry/drain protocol. Every protected effect must enforce its applicable fence; expiry alone does not revoke a running actor.” F owns the common substrate, M2 owns each effect boundary. No new deadline should be added to durable holds merely to satisfy this migration.

## Design decisions that need explicit closure (not assertions that current code is defective)

**D1 — Selection scope/lifetime and snapshot handoff location need one sentence of contract.** Section 3 explicitly protects existing mutable authority, but does not equally state how immutable object custody is preserved when price/workload evidence changes or a second host selects a realization. `FabricObjectRef` contains only a digest; `fabric_source_snapshot::materialize_source_snapshot` gets the manifest from the supplied store. There is no cross-backend object locator or automatic replication implied by that reference. Independently selecting a cheaper store at materialization can therefore select a store which never received the manifest. For the bounded delivery, recommend binding one selected logical storage authority/receipt to the capture-and-materialize handoff and passing that authority across execution contexts. A later choice may move/copy immutable objects only under an explicit admitted custody/materialization transition, not merely because the digest is unchanged. Assign A selection lifetime, F scoped binding/identity, and S preservation through handoff. This does not require a new global registry.

**D2 — Make the three-route / second-host acceptance matrix explicit.** “S through all three admitted realizations” is sound as route coverage, but cannot imply a local-only realization remains eligible for a workload that requires a second host to fetch the same source snapshot. The parent host's bare local disk is not reachable from that second host; serving it makes it the served-disk realization. State which control is local capture/materialize, which is actual cross-host handoff, and which complete three-candidate decision supplies the eligibility dispositions. Preserve truthful exclusions. A local-only workload can compare all three where admissible; a cross-host workload may properly exclude bare local files. Do not turn a route-forcing singleton into evidence that it won the complete field. The existing draft already requires the full decision and truthful scoped fields, so this can be a short clarification rather than a redesign.

**D3 — Enumeration registry ordering needs an explicit concurrent-writer obligation.** The proposed registration-before-first-value approach is coherent, but “registration precedes” must mean durably and independently established registration, not an attempted registration whose outcome is unknown. A lost registration CAS must re-observe/merge; a value cannot publish after a failed or unresolved registration. The reader must not silently omit a key from a complete listing because a registry page/read/refused traversal was missing. Add controls for two simultaneous first keys, interruption before/after registration, unknown registry publication, and complete listing after restart. F is correctly the owner. Avoid promising multi-key atomicity. One registry head also creates real contention: Cloudflare publishes a per-key write-rate limit, so the operation graph/cost and latency measurements must include registry contention rather than treating listing as a free adjunct.

**D4 — History must preserve the original publication, not a later reconstruction.** The history row is a good required contract. Add the discriminating condition that historical generation N returns the payload actually committed at N, including after a later writer and an unknown earlier head update. A separate append performed after head publication can lose a generation on interruption; competing candidates for the same next generation cannot both appear as committed history. F must define publication order and the recovery witness. This is particularly important for `approval_store_receipt` generation-1 reads, while the lifecycle migration must separately preserve generations/attempt identity even though most recovery paths read only the head. The draft does not claim this implementation exists; it should keep that honesty.

**D5 — Name the new domain model home, not only its staffing package.** Section 1 correctly says there is no complete storage SLO carrier today and A must model it. Recommend naming a proposed product-owned home, e.g. `gunbc.fabric.fabric_storage_selection`, for workload/service-requirement, typed eligibility/disposition roster, provenance/applicability and cost/latency projection. Keep generic operations in `std.fabric_storage`, algebra in `std.decision`/`std.pareto`, provider facts in their existing extdeps authorities, and placement/binding effects in their existing gunbc modules. This avoids A reading “storage interface remains std.fabric_storage” as permission to put fleet policy or vendor facts in std. Exact public type names can remain an A modeling deliverable.

## Smaller factual corrections

- Section 6's process row should say **event-driven belt entry**, not Timer. `gunbc.live_deploy.spec` lines 736–738 and 1117 onward explicitly retire the main belt timer. The separate credential-recovery timer remains real. The cited wrong-instance defect is real: `roadmap_belt_actuate::belt_actuate_spawn` line 3559 binds `srv1_live_dashboard_instance`, while `belt_tick_for_instance` passes its supplied instance into settlement and does not pass it into the launch fold.
- Section 2's complete binding shape is local files, door/socket, HTTPS served, unplaced and refused (`fabric_storage_client::FabricStorageBinding`, lines 50–55). If this row is meant as a shape inventory rather than a loose summary, list all five. The previous row correctly names door/socket.
- Section 3 should distinguish **unestablished evidence** (deferred / `SelectionNeedsEvidence`) from **missing structural join rows** (refused). `std.decision::decision_closure` defers typed `CausalModelUnestablished` and uncited grounds; missing/duplicate/foreign required coupling or sensitivity rows produce `DecisionClosureRefused`. “Missing ... evidence defers” is safe only if it means the former, not deletion of a required row.

## Findings that are sound and should survive revision

- R2: typed nonnumeric eligibility precedes numeric `HardConstraint`; candidate disposition completeness is not supplied by `establish_candidate_field`; no Boolean fake-cost axes. Cost plus latency, real source prices, account-level allowance/rounding, units and workload, and distinct immutable evidence identities correctly reflect the actual selector. `evidence_snapshot` equality is declaration identity, not value equality.
- R2: no observed latency is claimed. B1/B2 own collection and A owns admission; missing latency blocks a successful complete-field decision before S acceptance. No production metering platform is required. Canonical host-convergence composition and the deliberately unconsumed shared effect frontier are accurately distinguished.
- R3: served write uncertainty is owned by F, not assigned only to the R2 owner. Current curl/5xx mapping is accurately described. Get and namespace listing are distinct from closure. History and absent-target R2 gaps are real. Fixture release is explicitly outside ordinary durable delete authority.
- R4/R5: all six lifecycle consumers move in one authority cut; source namespace and deployed contents are separately accounted; no dual authority or post-write rollback from an old snapshot is promised. Typed incomplete unreadable-record recovery is clearly an intended tightening rather than claimed current behavior. Claim-before-add/readback, safe Git cleanup and independent removal readback remain obligations.
- R6: the two false-green claim tests are real: the helper returns `[]` on `WorktreeClaimPassRefused`. The plan does not claim required CI executes wet controls. S owns actual second-deployment execution and release, and source snapshot is identified as an instrument rather than an ordinary test label.
- R7: four seats cover the common substrate, provider readiness, lifecycle cut, and sequential other-consumer cohorts. F versus B is sufficiently explicit if B owns readiness/evidence/provider release and F owns execution protocol/results. V verifies handbacks rather than owning everybody's execution. No hidden second deployment owner remains.
- R8/R10: structural 64-bit addressing, one writer MAC on all `/state` operations, bucket-admin GET rather than universal readiness, and the source-bounded baseline are accurately qualified. I have not rerun the 15-module count or complete direct-consumer census here; that is R1's separate review.
- R9: the ledger paragraphs preserve rung limits, classify the file-root defect as source-proven rather than a fabricated live incident, and do not claim the design PR repairs the runtime.
