A named process/deployment below is a **source entrance or selector**, not proof that this revision is installed or that the store currently contains records. This complements the raw-Filesystem census: these consumers call a storage adapter and therefore do not necessarily name `Filesystem` themselves.

## Counts and dispositions

- The old section-E roster's **20 direct domain file-CAS modules** is accounted for below: **15 non-lifecycle modules (M1)** plus **five direct-CAS companion modules in the six-module lifecycle cut (C2)**. `work_provider_local` is the sixth lifecycle consumer; it reaches CAS through `attempt_lifecycle` rather than directly. Do not count that shared lifecycle adapter as another domain store.
- **14 external file-hold modules (M2)**: seven allocation-hold readers/writers, four commissioning-mutation readers/writers, and three host/printer/arrival modules. These form shared-state cuts, not 14 interchangeable object-store adopters.
- **Seven existing fabric-CAS consumer modules (F)** remain compatibility consumers. They are already on fabric and are not seven additional direct-file migrations.
- The four lower-level provider modules in the old 25-module file-CAS source census (`gunbc.durable_cas_file_store`, `gunbc.durable_exclusive_hold_file_store`, `gunbc.fabric.fabric_storage_file_store`, `extdeps.realization.materialization_store_local`) are backend/adapter work. They are not omitted consumers and are not M1 domain rows. Materialization's local hold and file operations belong to its own backend disposition.
- Exact immediate calls for the 15 M1 and 14 M2 modules are in `/tmp/cas-hold-direct-roster.json` (module, function, callee, source line). The root/entrance mapping below was read separately; a lexical caller count does not establish runtime reachability.

`Migrate` below means replace direct-file authority with the selected fabric authority while preserving the domain operation and recorded identity/history. It does not authorize a live cutover. `Compatibility` means retain the existing fabric consumer contract while the fabric backend/interface changes. An unactivated or canary-only consumer still needs an explicit migration or retirement decision; it must not be presented as deployed traffic.

## Required staffing / cutover conclusions

1. **M1 cannot be assigned as 15 unrelated root substitutions.** Approval decisions + generation-one receipts + enumeration move together. Device enrollment/counters share security identity. Commissioning's three CAS modules and four mutation-hold modules are one protected-state family. M1's `fabric_required_build_cell` is a hidden direct-CAS reader that belongs with M2 allocation holds.
2. **Allocation spans two authorities today.** Root-local hold generations and protected fabric workspace actor/owner/release records are joined by the controller. Migration must retain those joins and settle crash gaps; F is a required compatibility participant even if no F source requires changing.
3. **The target needs CAS, retained generation/history access where consumed, enumeration, hold acquire/release/recovery, protected input custody and equivalent refusal semantics.** Ordinary object put/get alone cannot close these cohorts. Preserve domain-specific operations; there is no requirement to immortalize every obsolete internal file-store helper in a new generic protocol.
4. **Readiness is root-produced once.** The current file CAS does not create missing roots. Modeled setup exists for approvals/auth claims, devices, boot/unit holds, dashboard directories, allocation and commissioning; assertion-counter and printer setup need an explicit producer or an honest preexisting-state admission. SCM/caller-backlog have explicit caller roots and no activated production deployment producer found.
5. **Inventory before switching; never initialize fresh and call it migration.** For each root/namespace: establish actual host/instance/principal and current contents, fence writers and recovery readers, preserve generations/IDs/needed history and companions, independently reconcile the selected backend, then switch the whole cohort. Observe open/held/terminal-but-unsettled work, not only current happy-path records. This is design scope, not authorization to run that procedure now.
6. **Do not promote comments into deployment evidence.** Allocation's old only-live-instrument comment and file-CAS's old two-authorization-consumer comment lag source evolution. Caller backlog's unactivated standing, however, is corroborated by the lack of a production call to the durable worker entry. All actual installed state remains unobserved by this audit.
