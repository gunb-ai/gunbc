Scope is all ten tracked Swift files under `apps/approve-ios`, plus the repository's two tracked C/JavaScript files. ## Adjacent server state reached by the phone — migrate with approval cohort

The Swift app should retain its existing domain protocol while these server writers/readers consume fabric. The program must not confuse keeping hardware/Keychain custody with excluding server approval data from the migration.

* `gunbc.auth.approval_device_redemption::{approval_device_store_directory,device_store_write,observe_enrolment_slot,observe_enrollment,issue_enrolment_code,commit_enrolment,revoke_enrolment}` owns code/enrollment/revocation records and generations. Preserve single consumption, key/App Attest identity, revocation and readback. Root supplies admitted fabric namespace; physical server store population must be observed before cut, not assumed empty because this app is incomplete.
* `gunbc.auth.approval_device_routes::{device_enrol_response[_at],device_redeem_response[_at],device_pending_response[_at],device_request_response[_at],device_enrollment_readback_response[_at],device_push_update_response[_at]}` remains the domain boundary. Request/decision/counter stores are the approval cohort already inventoried by the parent; keep assertion counters, request revisions, capability/proof validation and independent request text.
* **Push registration is an extra non-CAS durable cohort:** `approval_device_routes::{approval_device_push_root,push_registration_path,store_push_registration}` writes owner-only last-write-wins JSON at `/var/lib/gunbc/approval-device-push/<verified-enrollment-id>.json`. Writers are enrollment and push-update paths. This belongs behind fabric under existing verified enrollment authority; migrate existing registrations or explicitly disposition them without silently dropping notification state. Preserve owner-only confidentiality and verified-id keying. It must not share the raw enrollment CAS-generation layout accidentally. No DAG provisioning consumer of the push-root symbol or its literal path was found; the writer is a file write, not a parent-directory ensure. Treat push-root readiness as a source gap to resolve at the fabric/deployment root, not evidence of a known live failure.
* `approval_device_routes::approval_device_push_sender_frontier` explicitly says there is NO corpus APNs sender yet. The future reader attaches at `approval_request_submission::notify_filed`, reads the verified operator's registration and uses a separately provisioned APNs signing secret. Source-defined registration writes are not an executed push pipeline; do not promise an existing reader/call site. The APNs signing key, when provisioned, remains credential custody, not ordinary durable application bytes.

## Existing model, gaps and evidence limits

`gunbc.approve_ios_enrolment_machine` already models full payload/record rendering and persist-before-effect admission: `PreparedEnrolmentPayload`, `EnrolmentState`, `enrolment_record_render`, `enrolment_record_digest`, `enrolment_persist`, `EnrolmentEffectAdmission`, `enrolment_effect_admitted`, `enrolment_call_admitted`. Its own comments disclose that the supplied CAS observation/decision is not a store-minted execution receipt. `approve_ios_enrolment_state_generator_frontier_rows` explicitly reserves the missing EnrolmentState.swift generator/realization connection. The Swift phase machine is generated, but EnrolmentState/AppState persistence remains hand-authored. Reuse that authority; a fabric-interface plan must not claim real OS persistence is already sealed by the pure model.

`gunbc.approve_ios_app::approve_ios_device_keys_retained` retains Apple custody glue until extdeps models the actual CryptoKit/DeviceCheck/Keychain call shapes and Swift emits them. This is an existing backend frontier, not permission to export private keys. `approve_ios_enrolment_state_frontier` names the handwritten domain state gap. The local JSON encoding is currently Swift Codable, while the model has its own record render; compatibility requires an explicit joined encoding/migration, not changing serialization silently.

One observed source weakness matters to a migration handoff: `AppState.install` starts with `.unenrolled`, catches `EnrolmentStore.load` errors into `lastError`, and leaves the state `.unenrolled`. `KeychainItem.read` distinguishes missing from unreadable, but this outer UI state does not. Do not describe current behavior as a typed unreadable-store refusal or carry that flattening into a new interface; ensure unreadable/malformed existing enrollment cannot be silently treated as empty during initialization or migration. No fix is attempted here.

The source build standing is explicit: `approve_ios_build_receipts` is empty; `approve_ios_build_standing` says no required lane executes the iOS build. It records a relayed 2026-09-24 simulator test sentence as insufficient provenance, not an accepted receipt. This audit does not establish whether any operator phone currently has an installed app, Keychain record, enrolled/unknown/revoked identity, real APNs token, valid signing entitlements, or successful roundtrip. These are deployment observations required before an operational cut, not facts to invent from the repo. No out-of-repository consumer search is claimed or required by Brian's scope.

## Suggested concise plan prose

“The iOS app's sole explicit durable client record is enrollment state in the Apple Keychain, including device-bound wrapped-key custody and the exact retry material needed before contacting the server. Retain that admitted platform realization and join its logical persistence/effect boundary to the existing enrollment model; do not relocate enclave/App Attest keys or make initial enrollment depend on a remote store. Server enrollment, assertion/decision state and owner-only push registrations migrate behind fabric through the existing approval routes. Pending UI state, the ephemeral HTTP session, immutable test vectors, and the C/JavaScript fixtures are explicitly not durable-data migrations. Existing phone state and real device execution remain unobserved until a named deployment check establishes them.”
