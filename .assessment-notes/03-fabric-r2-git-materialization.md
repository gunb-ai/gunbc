## Fabric today: facts suitable for the revised plan

`std.fabric_storage` is the existing metadata interface: immutable structured `FabricObject { links, body: NonEmptyStr }`, `FabricObjectRef`, conditional named heads, get-by-ref result, and bounded linked closure. Metadata is retained history, not an evicting materialization cache. `FabricObjectMissing` is refusal for a required object; `FabricHeadAbsent` is a readable absent head; these are distinct. `FabricHeadMoved` is contention, not a fault. `FabricClosureBudgetExhausted` refuses instead of returning an apparently complete truncated chain.

`gunbc.fabric.fabric_storage_client::FabricStorageBinding` currently has LocalFiles, DoorSocket, Served, Unplaced and Refused. There is no R2 arm. Its executable operations are `fabric_storage_put`, `fabric_storage_head`, `fabric_storage_advance`, and `fabric_storage_closure`, plus `fabric_storage_presented_identity`. The client has NO get-by-ref, list/enumeration, or delete operation. `FabricObjectGet` already exists and is used by the file/R2 adapters; a client get is a missing connection, not a reason to invent another object result. Enumeration, retention/release, and complete R2 metadata composition require explicit modeled contracts.

`gunbc.fabric.fabric_storage_binding::{fabric_storage_placement,fabric_storage_binding_for,fabric_state_storage_binding}` receives the production role realization. Same-host public metadata clients use the restricted Unix door; remote clients use HTTPS. Protected-state clients always use signed HTTPS, including the placed host. `FabricStorageLocalFiles` remains a valid serving implementation, injected fixture and separately scoped host-capacity ledger binding; it is not the placed shared-state bypass. The role's host/root/endpoint is selected by `fabric_storage_placement::fabric_storage_placement_under`; an unavailable/refused role does not fall back to srv1 or a local copy.

`fabric_storage_placement::{fabric_storage_store_directories,fabric_storage_directory_demands,fabric_storage_state_directory}` declares store root, objects, heads, separate state root/objects/heads, door and control directories for the placed instance. The service principal alone writes the physical shared store (root/the service can of course act outside that API). These declarations feed live deployment. The store is retained on deployment retraction. `fabric_storage_file_root_ensure`, separately used by host capacity and fixtures, only runs Mkdir.Parents for objects/heads and treats exit success as Ready: it does not establish owner/mode/readback. Repair and migrate all direct consumers, including the 15 test modules listed below.

`docs/plans/fabric-storage.md` is important historical design, but several present-tense passages are superseded: placed-host clients no longer bypass the door; the previously missing writer roster now exists; R2 ETag-conditioned head operations now exist. Its 2026-09-21 empty srv1 store observation is historical and cannot establish today's population. Its fabric-event-log Git cutover/drain is about THAT event log, not the still-Git-backed roadmap event carrier.

### Access and identity boundaries to preserve

* Public metadata: `fabric_storage_serve::fabric_served_storage_respond` admits put/advance through `fabric_writer_roster::fabric_door_writer_admission_over`; head/closure and identity remain readable to peers reaching the public door. This does not establish permission to expose private objects by a new public get route.
* Protected `/state`: `fabric_storage_protected_door_over` requires the trusted proxy peer or an admitted direct local peer; then `fabric_storage_state_serve::fabric_storage_state_serve_over` requires the exact authenticated route and a valid MAC envelope. Proxied tagged clients need not have a rostered user login; the signed service envelope is their state admission. This is not accurately described as requiring the public user-login roster for every state request.
* `fabric_storage_state_auth::{fabric_state_operation,fabric_state_sign,fabric_state_verify,fabric_state_decode_verified}` currently allows head/closure/advance/put only. Key id `fabric-state-writer/1` is a distinct service authority, not an approval key. Signed content binds audience, operation, request and issued_at; accepted age is 0–60 seconds. The same key admits reads and writes; there is no per-consumer tenancy identity in the envelope. `fabric_storage_state_auth_io::fabric_state_keyring` reads an installed key or an absolute configured `GUNBC_FABRIC_STATE_KEY_FILE`; invalid configuration refuses. New get/list/release work must preserve this boundary and must not silently widen ordinary write authority to deletion.
* Metadata refs currently use `std.content_hash::Fnv1a64Structural`, 64 noncryptographic bits, through `std.fabric_storage::fabric_object_ref_of`. This is a declared locator limitation, not cryptographic identity or tenant isolation. Put checks existing preimage equality; get verifies the structural ref, which is not an adversarial second-preimage guarantee. The known SHA-256/native-emission frontier and family migration live in `fabric_object_identity_is_a_structural_locator` and the historical fabric plan. R2 blob/origin SHA-256 readings do not automatically upgrade metadata refs. A family migration must measure stored population and update parser, links and owning payload codecs (event parent refs also occur inside payload bodies).

## Source-snapshot first consumer and released R2 fixture

Current concrete metadata consumer `fabric_source_snapshot::{capture_source_snapshot,materialize_source_snapshot}` has one external code consumer module, `gunbc.instruments.source_snapshot_handoff`. The unchanged no-argument instrument is an end-to-end executed integration entry, not an already-deployed production workflow. It acquires a compiler binary; creates synthetic public/v2/test source inclusions; captures; materializes into `ProviderWorkspace`; runs a real child process; checks mismatch/missing/corrupt/escape/duplicate/unsafe-allocation/squatted-base controls; releases workspaces. Ordinary snapshot helpers lose concrete file-root operands; intentionally destructive file-provider fixtures stay explicit isolated provider controls. Capturing metadata does not move local source paths, provider workspace or child execution into object storage.

The R2 pilot cannot truthfully claim isolated release merely by selecting existing `FabricWorkspace`: its retention is released-never and keys are global `objects/<ref>`. Nor does using `FabricCacheBlobs` automatically release these metadata objects: its lifecycle scope is `blobs/`, not `objects/`. Required DESIGN task before executing the R2 pilot: model an admitted fabric-owned fixture binding with isolated bucket/namespace, bounded synthetic population and no production head/state authority; root resolves it once for capture/get; explicit fixture release authority tracks every possible publication (including uncertain writes), performs release, and independently establishes absence. Account separately for local staging and credential cleanup. Use existing low-level R2 delete/lifecycle provider capabilities as implementations after the domain contract is modeled, never add hand-rolled delete loops to snapshot consumers or grant delete to ordinary durable callers. A release that is refused/unknown keeps an outstanding obligation and cannot report a fully clean pilot success. No new resource provisioning/execution is authorized by this design-only work.

Example selection 0/0 versus positive values remains explicitly supplied standing for a fixed operation workload; it proves route choice only alongside actual selected put/get/readback evidence. It is not measured whole-snapshot economics, production rollout or compiler-inferred prerequisites. Each positive backend route needs wrong-scope/access, failed/missing readback, unresolved publication and failed cleanup controls, while intentional file corruption/hole controls remain isolated.
